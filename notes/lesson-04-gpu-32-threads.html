Lesson 4. The picture on 32 GPU threads

This lesson covers Lab 1, part 2, on the GPU, where you write mandelbrot_gpu_vector and launch_mandelbrot_gpu_vector. It needs an NVIDIA GPU, and Nsight Compute (ncu) for one profiler measurement. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

The GPU half of Lab 1, part 2 launches 32 threads instead of 1, <<<1, 32>>>, and has each thread take its share of the places by its own number, threadIdx.x. The usual split gives thread t the places j = t, t + 32, t + 64, and so on, and it is usually defended on the grounds that neighbouring threads touch nearby memory. Inside one thread, however, the places 7 and 39 are 32 apart, and threads do not talk to each other; and each thread executes its own while loop, so the 32 threads need different numbers of repetitions. Where is the nearby, and what do 32 threads with different counts cost?

Both objections were raised at this step, in these words:

"no proof this how can 7 and 39 and all be nearby stuff" / "On one hand you are saying nearby, and on one hand you are saying spacing. You cannot space out and do nearby at the same time" / "Threads don't talk to each other. A thread doesn't know about other threads, right?"

Write a guess. With 32 GPU threads instead of 1 on the same picture, what speedup do you expect: 32, about 22, or about 8?

Inside one thread the places are 32 apart

__global__ void mandelbrot_gpu_vector(uint32_t img_size, uint32_t max_iters, uint32_t *out) {
    for (uint64_t i = 0; i < img_size; ++i) {
        for (uint64_t j = threadIdx.x; j < img_size; j += blockDim.x) {
            /* cx, cy, and the scalar while loop that makes iters */
            out[i * img_size + j] = iters;
        }
    }
}
mandelbrot_gpu_vector<<<1, 32>>>(img_size, max_iters, out);

Read in English, the first line marks a kernel with __global__, a function that executes on the GPU and hands nothing back, and it receives img_size, max_iters and out, the address of the output array in the graphics card's memory. The kernel gives i every value from 0 to img_size - 1, one after another; for each i, a thread's j begins at its own number, threadIdx.x, and grows by blockDim.x, the number of threads in the block, while it stays below img_size; for each j the comment stands for the cx line, the cy line and the scalar while loop that makes iters, and the thread stores the count at place i times img_size plus j. The last line starts the kernel from the CPU as 1 block of 32 threads, every thread executing the whole kernel.

In thread t, threadIdx.x is t, from 0 to 31, and blockDim.x is 32. The GPU chip is built from identical blocks of hardware, which NVIDIA calls SMs, and an SM handles the threads of a block in consecutive sets of 32, beginning each instruction for all 32 at once, each thread with its own i, j and count; NVIDIA's CUDA programming guide calls such a set a warp.

Write j as t + 32 x k and list the values thread 7 takes for one i. Which thread, and which k, stores j = 103?

CHECK

Thread 7 takes 7, 39, 71, 103, 135, 167, 199 and 231, for k = 0 to 7, and 103 = 7 + 32 x 3, so thread 7 stores it at k = 3. Inside one thread the places are 32 apart: the objection is right for one thread.

Across the 32 threads of one store, the places sit side by side in 4 blocks of 32 bytes

The store out[i * img_size + j] = iters executes for all 32 threads of the warp together, with the same i and k, and each value takes 4 bytes, so thread t writes the 4 bytes that begin at byte 4 x (i x 256 + t + 32 x k). Memory moves bytes in blocks of 32 that begin at a multiple of 32; Nsight Compute, NVIDIA's profiler, calls one store instruction for the 32 threads a request, and each 32-byte block it touches a sector.

For i = 0 and k = 0, thread 0 writes bytes 0 to 3. Write which bytes thread 31 writes, how many 32-byte blocks the store touches, how many store instructions the whole picture needs, 256 values of i times 8 of k, and how many blocks they touch in all.

CHECK 
thread 31: bytes 124 to 127; together, bytes 0 to 127 with no gap
blocks per store instruction: 128 / 32 = 4
store instructions: 256 x 8 = 2,048;  blocks: 2,048 x 4 = 8,192

Take the other split, where thread t takes j = 8t to 8t + 7. In the first store thread t writes j = 8t; write its byte, the number of blocks the 32 threads touch, the total for the whole picture, and the factor against 8,192.

CHECK

Thread t writes byte 32t, so the 32 threads write bytes 0, 32, up to 992, each in a block of its own: 32 blocks per store instruction, 2,048 x 32 = 65,536 in all, 8 times 8,192.

Inside one thread the places are 32 apart; across the 32 threads of one store they sit side by side. Both are true, and memory receives only the second.

Nsight Compute counts both numbers on a real execution.

ncu --metrics l1tex__t_requests_pipe_lsu_mem_global_op_st.sum,l1tex__t_sectors_pipe_lsu_mem_global_op_st.sum ./mandelbrot_gpu -i vector

Read in English, the command executes the program under the profiler and prints, for each kernel launch, the number of store requests and the number of 32-byte sectors they touched.

Write your printed requests and sectors beside the laptop's 2,048 and 8,192, and say whether they match the count by hand.

CHECK

The laptop's profiler printed 2,048 requests and 8,192 sectors, exactly the count by hand: the nearby is that each store instruction of 32 threads lands in 4 blocks of 32 bytes.

If ncu prints ERR_NVGPUCTRPERM, the driver hides its counters from ordinary users; executing ncu with sudo, or allowing access in the driver's settings, lifts it.

Writing the kernel, and a launch that prints 0 while doing the work 32 times

The kernel is the code above with the reference's body inside the j loop, cx, cy, the while loop and the count, and the launch function starts it with <<<1, 32>>>. A launch written as <<<32, 1>>> instead also prints a difference of 0, with a time close to one thread's, because each of its 32 blocks has blockDim.x = 1 and threadIdx.x = 0, so every block computes the whole picture.

Compile, execute ./mandelbrot_gpu -i vector, and write the printed difference.

CHECK

A correct version prints exactly 0, and about 0.248 means nothing was stored, a missing launch or a kernel that never executed.

Finished threads wait, so 32 threads gave 22.75 times, not 32

Measured on the laptop for the 256 by 256 picture at max_iters 1000, one GPU thread took 403.435 ms and 32 threads took 17.732 ms. Since an instruction begins for all 32 threads of the warp at once, the while loop keeps beginning instructions until the last of its 32 threads has left it, and the threads already done wait. A thread doing one repetition will be called a thread-repetition here: each repetition of the warp costs 32 of them, and the useful ones add up to the counts.

Work out the measured speedup. Then take a real moment of the loop, i = 40 and k = 5, where j goes from 160 to 191, one place per thread; the largest count is 1000 and the 32 counts add up to 1,334. Work out the thread-repetitions and the useful share. Over the whole picture 16,274,722 of 23,609,216 thread-repetitions are useful; work out 32 times that share as the speedup predicted when only thread-repetitions cost time.

CHECK 
measured: 403.435 / 17.732 = 22.75
i = 40, k = 5: 32 x 1000 = 32,000 thread-repetitions, 1,334 useful, 4.2 percent
whole picture: 16,274,722 / 23,609,216 = 0.6893;  32 x 0.6893 = 22.06 predicted

Threads waiting for the slowest thread of their warp explain most of the gap between 32 and 22.75.

A single line decides both the memory traffic and the waiting

Gathered together, each store instruction lands in 4 blocks of 32 bytes; the split into consecutive pieces per thread would move 8 times more; the profiler confirms 2,048 and 8,192; and the useful share of thread-repetitions predicts 22.06 against 22.75 measured, the GPU's version of the 88.8 percent that 8 neighbours reach on the CPU.

Write one sentence on what the line for (j = threadIdx.x; j < img_size; j += blockDim.x) decides.

CHECK

It decides which 32 places share one store instruction, side by side, so 4 blocks instead of 32, and which 32 places share one while loop, neighbours, so similar counts and 69 percent useful.

The reading "32 threads give 32 times" fails, because the threads of one warp wait for its slowest place.

The Fall 2025 handout's third question asks how the vector version compares with the scalar ones and how the GPU handles copies of the kernel that need different numbers of repetitions; 22.75 measured against 22.06 predicted answers the first part, and the warp that keeps executing until its slowest thread is done, with the finished threads waiting, answers the second. A sector count 8 times the hand count means the places were split in consecutive pieces per thread.

Without code, the 32 threads move through the program together, so when their pieces of work are unequal the quick ones wait for the slow one, and workers that must finish together are as fast as the slowest of them. The way the work is dealt out also decides how much memory traffic it causes, here by a factor of 8, so how the work is handed out matters as much as how many workers there are.

The guess at the top has its answer: about 22, measured 22.75 from 403.435 ms against 17.732 ms, predicted 22.06 from the useful share of thread-repetitions.

A harder question to finish with. Launch the same kernel as <<<1, 64>>>. Predict the profiler's requests and sectors, the useful share of thread-repetitions, and the time, before measuring.

CHECK

Each warp w now takes j = 32w + t + 64k, so its 32 threads still store 32 places side by side: requests stay 2,048 and sectors 8,192. The sets of 32 places that share a loop are the same sets as before, j = 0 to 31, 32 to 63 and so on, so the useful share stays 0.689. What changes is that there are 2 warps, which can sit on 2 of the SM's 4 schedulers, the circuits that pick which warp's instruction begins next, so the time can fall to about half of 17.732 ms, which a measurement has to confirm.
