The story

The GPU half of Lab 1, part 2 launches 32 threads instead of 1, <<<1, 32>>>, and has each thread take its share of the places using threadIdx.x, the thread's own number. The usual split gives thread t the places j = t, t + 32, t + 64, and so on.

The learner was told this split is good because neighbouring threads touch nearby memory, and refused: inside one thread the places 7 and 39 are 32 apart, and threads do not talk to each other. Then a second question: each thread executes its own while loop, so what happens when the 32 threads need different numbers of repetitions?

Where exactly is the nearby, and what do 32 threads with different counts cost?

Work it out

L01 The learner's kernel and launch, with the scalar while loop shortened, copied from page 06: from: your code

__global__ void mandelbrot_gpu_vector(uint32_t img_size, uint32_t max_iters, uint32_t *out) {
    for (uint64_t i = 0; i < img_size; ++i) {
        for (uint64_t j = threadIdx.x; j < img_size; j += blockDim.x) {
            /* cx, cy, and the scalar while loop that makes iters */
            out[i * img_size + j] = iters;
        }
    }
}
mandelbrot_gpu_vector<<<1, 32>>>(img_size, max_iters, out);

L02 CUDA facts: in thread t, threadIdx.x = t (0 to 31) and blockDim.x = 32. An SM handles a block's threads in consecutive sets of 32, which NVIDIA calls warps; an instruction begins for all threads of a warp at once, each thread with its own i, j and iters. from: CUDA programming guide (SIMT architecture)

L03 DO From L01, in thread t, j takes t, t + 32, t + 64, ... while j < 256; write j = t + 32 x k. Thread 7's values of j = ____ . The thread and k that store j = 103: t = ____ , k = ____ . from: L01, L02

CHECK

Inside one thread, the places are 32 apart: your words are right for one thread.

L04 Facts: the store out[i * img_size + j] = iters executes for all 32 threads together, with the same i and k; each value is 4 bytes, so thread t writes the 4 bytes that begin at byte 4 x (i x 256 + t + 32 x k). Memory moves bytes in blocks of 32 bytes that begin at a multiple of 32. The profiler calls one store instruction for the 32 threads a request, and each 32-byte block touched a sector. from: L02, L03, CUDA programming guide, Nsight Compute metric names

L05 DO i = 0, k = 0: thread 0 writes bytes 0 to 3, thread 31 writes bytes ____ to ____ . 32-byte blocks touched = ____ . Store instructions for the whole picture = 256 values of i x 8 values of k = ____ ; blocks touched = ____ . from: L03, L04

When it goes wrong

  • Difference 0, but the time is close to one thread's. The launch was <<<32, 1>>>: 32 blocks of 1 thread, where threadIdx.x is 0 and blockDim.x is 1, so every block computes the whole picture.
  • Difference about 0.248. Nothing stored: the launch is missing or the kernel never executed (L08).
  • ncu prints ERR_NVGPUCTRPERM. The driver hides the performance counters from ordinary users: execute ncu with sudo, or allow access in the NVIDIA driver settings.
  • The sector count is 8 times L05. The places are split in consecutive pieces per thread, as in L06.

In plain words

On a GPU, 32 threads move through the program together. When their pieces of work are unequal, the quick ones wait for the slow one, so 32 threads gave about 22 times, not 32. The way the work is dealt out also decides how much memory traffic it causes, here a factor of 8.

For a manager: a team that must finish together is as fast as its slowest member. How work is handed out matters as much as how many workers there are.
