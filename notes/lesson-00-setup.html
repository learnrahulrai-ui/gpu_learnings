Lesson 0. Set up your machine and read the starter program

This lesson comes before Lab 1 and builds nothing. It puts the starter code of both labs on your own computer, compiles it, and reads what the untouched program prints; it needs Linux or WSL2 on Windows, g++ and git, and for the GPU half an NVIDIA GPU with its driver and the CUDA toolkit. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

Students enrolled in MIT 6.S894 send their code to the course's machines with a tool called telerun, which needs a course account. Without one, every lab here is compiled and timed on your own computer, and that changes three things at once: which CPU instructions exist, which GPU executes the kernels, and every number you measure. Every measured number on these pages comes from one laptop, a Ryzen 5 4600H CPU with a GTX 1650 GPU, so each of yours can be set beside it.

The first question at this point, asked by the owner of that laptop, was whether any of this depends on installed software:

"Even if I don't install CUDA libraries, even if I don't even open NVIDIA website ever on my laptop, these things just remain, yes or no" / "A block need not exist at all. But wrap scheduler always exists. So why would a wrap scheduler even know about blocks" / "the total number of threads which I can run on my hardware is what? 14 times 4 times 32, is this true or false?"

It does not. The instructions a CPU has and the generation a GPU belongs to are fixed in the chips, and both can be read off before a single line is compiled. The starter program, too, can be compiled and executed before you write a line of your own: it times the reference function, compares your function with it, and prints a result even while your function is still empty. What does a function that does nothing print, and how does that one number tell you whether your setup works?

Before compiling anything, write down a guess. The vector function in the Lab 1 starter is empty, yet the program still compares its output with the reference and prints an "average output difference". Is the printed number 0, 1, or something in between, and if in between, which value?

Lab 1 assumes 16 floats per instruction, and the laptop has 8

The Fall 2025 Lab 1 handout targets AVX-512, CPU instructions that act on 512 bits at once, and a float takes 32 bits. The Ryzen 5 4600H in the laptop has AVX2 instead, whose instructions act on 256 bits. On Linux or WSL2 the CPU lists the instruction sets it has in /proc/cpuinfo, and one command picks out the two that matter here.

grep -o -w -e avx2 -e avx512f /proc/cpuinfo | sort -u

Read in English, the command searches the CPU's own description for the words avx2 and avx512f and prints each word it finds, once.

Divide 512 by 32 and 256 by 32 to get the floats per instruction of each set. Then execute the command and note which of the two words your CPU printed, since that decides how many places your Lab 1 vector code can handle per instruction.

CHECK

AVX-512 holds 512 / 32 = 16 floats and AVX2 holds 256 / 32 = 8. The laptop prints only avx2, because its Zen 2 cores have no AVX-512, so its vector code works on 8 places per instruction.

Code written with AVX-512 instructions stops on such a CPU with "Illegal instruction" at the first one it reaches.

Your GPU's generation is the number after -arch

An NVIDIA GPU belongs to a generation, named by a pair of numbers called its compute capability, which NVIDIA's CUDA programming guide lists for every GPU; the GTX 1650 is 7.5, the generation NVIDIA calls Turing. The nvcc flag -arch=sm_75 makes nvcc produce machine instructions for 7.5, so a listing of the compiled file shows exactly what that GPU executes. A value that does not match the GPU gives a program whose kernels never begin, and it reports "no kernel image is available for execution on the device". The driver and the toolkit report what is needed.

nvidia-smi --query-gpu=name,compute_cap --format=csv
nvcc --version

The first line asks the NVIDIA driver for the GPU's name and compute capability, printed as comma-separated text; the second prints the version of the CUDA compiler.

Write your GPU's name and compute capability, the -arch flag that follows from it, and your nvcc version.

CHECK

The laptop reports an NVIDIA GeForce GTX 1650 with compute capability 7.5, so its flag is -arch=sm_75, and its nvcc is release 12.4.

If nvcc stops with "unsupported GNU version", your g++ is newer than your CUDA version accepts. NVIDIA's installation guide for your CUDA version lists the accepted ones, and nvcc's -ccbin option points it at an older g++ once one is installed.

Fetching the labs takes four commands, and the last prevents a silent failure

git clone https://github.com/accelerated-computing-class/lab1.git
git clone https://github.com/accelerated-computing-class/lab2.git
cd lab1
mkdir -p out

The first command copies the Lab 1 starter code from the course's public repository into a new folder named lab1, and the second does the same for Lab 2. The third moves into lab1. The fourth makes a folder named out, where the program writes its pictures; when that folder is missing the program writes none and reports nothing, so an execution that finishes without pictures is the first thing that can go wrong without any message.

The file mandelbrot_cpu.cpp holds three things: mandelbrot_cpu_scalar, the reference, already written; mandelbrot_cpu_vector, empty, which part 2 of the lab asks you to write; and a main that computes the reference once, then times each version and prints its time, and for the vector version also its average output difference from the reference. The picture is 256 by 256 places with at most 1000 repetitions each, unless the flags -r and -b set other values.

g++ -O3 -march=native -std=c++17 mandelbrot_cpu.cpp -o mandelbrot_cpu
./mandelbrot_cpu

In the first line, -O3 asks for full optimization, -march=native allows every instruction this CPU has, AVX2 included, -std=c++17 selects the 2017 C++ standard, and -o names the program mandelbrot_cpu. The second line executes it with the default picture.

The starter times each version with a macro named BENCHPRESS, which calls the function 10 times, times each call, sorts the 10 times and prints the smallest.

The laptop printed 61.6 ms as the time of mandelbrot_cpu_scalar. Write your own time and divide it by 61.6. Then work out why the starter prints the smallest of its 10 calls rather than their average, given that another program on the machine can only ever make a call slower.

CHECK

A disturbance only adds time, so the smallest of the 10 calls is the one closest to what the code itself costs. The price is that the smallest hides how much the calls varied: the times 10, 11, 10, 30 and 14 ms print as 10.

Your ratio to 61.6 is the factor to keep in mind whenever a later time of yours is set beside the laptop's.

An empty function prints 0.248, and that number proves the check works

Before the vector version is timed, main fills its result array with 0. Afterwards it adds up, over every place, the gap between the result and the reference's count of repetitions, and divides the sum by img_size times img_size times max_iters. On the laptop, the reference's counts for the 256 by 256 picture add up to 16,274,722, a total that a few added lines of its main printed as the CPU total.

With mandelbrot_cpu_vector still empty, the result stays 0 at every place. Work out the printed difference, 16,274,722 divided by 256 times 256 times 1000. Then work it out a second way, as the average count per place, 16,274,722 / 65,536, divided by max_iters, 1000. What must a correct vector version print?

CHECK 
256 x 256 x 1000 = 65,536,000
16,274,722 / 65,536,000 = 0.2483

16,274,722 / 65,536 = 248.3 repetitions per place
248.3 / 1000 = 0.2483

Both ways give 0.2483: an empty function is wrong by the whole picture, and a correct version prints exactly 0. If your machine prints about 0.248 now, both the reference and the check work.

The GPU file follows the same pattern; compile and execute it with your own number in place of 75.

nvcc -O3 -arch=sm_75 -std=c++17 mandelbrot_gpu.cu -o mandelbrot_gpu
./mandelbrot_gpu

The first line compiles the CUDA file with full optimization, for compute capability 7.5, as 2017 C++, into the program mandelbrot_gpu. The second executes it: it computes the reference on the CPU, then times the two GPU versions.

Its timing differs from the CPU file's. It repeats a measurement 5 times, and each time it calls the launch function 3 times, waits for the GPU to finish with cudaDeviceSynchronize and divides the time by 3; it prints the smallest of the 5 results. The launch functions in the starter are empty, so they start nothing on the GPU.

Write the difference you expect for each empty GPU version, and what the printed time of an empty launch function measures. Which of all your versions prints the shortest time?

CHECK

About 0.248 for both, for the reason computed above. The printed time is three calls of an empty CPU function plus a wait on an idle GPU, a few microseconds.

The empty versions print the shortest times of all, so a short time next to 0.248 is a function that did nothing.

A time printed without its difference proves nothing

This page has produced the numbers every later lesson is measured against: how many floats your vector instructions hold, 8 on the laptop or 16 with AVX-512; the -arch value of your GPU; your scalar time beside the laptop's 61.6 ms; and the 0.248 that an empty function prints, together with the fact that the empty functions also print the shortest times.

Write those three reference numbers on one line, and under them one sentence on why a printed time without the printed difference proves nothing.

CHECK

Your floats per instruction, your scalar time, which is the baseline of every later speedup, and the difference, 0.248 for an empty function and exactly 0 for a correct one.

A time says how long something took, not what it computed, and the empty functions print the shortest times of all. So the reading "it compiled, finished and printed a time, so the setup works" does not survive this page: an empty function also compiles, finishes and prints a time.

Before any of this, the setup can stop with a message. "Illegal instruction" as soon as a vector version begins means AVX-512 code on a CPU that has only AVX2; "unsupported GNU version" from nvcc means a g++ newer than your CUDA version accepts; "no kernel image is available for execution on the device" means an -arch value that does not match the GPU. The silent failures are worse: a missing out folder leaves no pictures and no message, and an empty or missing launch leaves 0.248 and a tiny time.

Without any code, the point of this lesson is that two instruments come before any speed-up, a clock and a check that the output is right. A function that does nothing tests both at once, because the clock must show it as fast and the check must show it as completely wrong, and a report that shows only times can rank such a function first.

The guess at the top has its answer now: the empty function prints about 0.248, which is 16,274,722 / 65,536,000, the average of 248.3 repetitions per place divided by 1000.

A harder question to finish with. The GPU file prints a few microseconds for the empty launch function, and a colleague calls that the cost of one kernel launch and subtracts it from every later GPU time. What is wrong with that, and what would measure the cost of a launch?

CHECK

The empty launch function launches nothing, so its time is three calls of an empty CPU function plus cudaDeviceSynchronize on an idle GPU. A real launch also hands a kernel to the GPU and waits for it to begin and end.

Timing an empty __global__ kernel launched <<<1, 1>>>, 3 times followed by one cudaDeviceSynchronize, exactly as the starter times the real kernels, measures that cost, and only measurements taken the same way may be subtracted from each other.

Page 00 of the lab pages, what a GPU is, measured on one laptop, sets the laptop's CPU and GPU side by side in full, and page 15, what the two printed numbers can hide, takes the printed difference apart. The short notes on the block of hardware a GPU chip is built from and on what the printed difference can hide cover the same ground in a minute each.
