Lesson 2. The picture on one GPU thread

This lesson covers Lab 1, part 1, on the GPU, where you write mandelbrot_gpu_scalar and launch_mandelbrot_gpu_scalar in the starter file mandelbrot_gpu.cu. You need an NVIDIA GPU with its driver, the CUDA toolkit, and the Lab 1 starter folder, fetched with git clone https://github.com/accelerated-computing-class/lab1.git. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

The first GPU task of Lab 1 moves the reference function, mandelbrot_cpu_scalar, onto the GPU unchanged and has a single GPU thread execute all of it. It needs a pair of functions: a kernel, which executes on the GPU, and a launch function, which executes on the CPU and starts the kernel. The Fall 2025 handout's first question asks how the time of this GPU version compares with the time of the reference on one CPU core, and what explains each. What does one GPU thread have, compared with one CPU core, and which measured number shows it?

The question underneath it, in the words of the owner of the laptop these pages measure, was what the step from definitions to a working kernel consists of:

"I know what is GPU and I know what is threadIdx ... But what is the exact intellectual step I have to do?" / "any idiot can say we will put all the things in parallel because they all work on the GPU"

Write a guess. Measured on the laptop's Ryzen 5 4600H, one CPU core computed the starter's default picture, 256 by 256 places, in 61.6 ms. How long does one thread of the laptop's GTX 1650 take for the same work: less, about the same, or more? Write a number.

Reading the reference that the kernel has to repeat

void mandelbrot_cpu_scalar(uint32_t img_size, uint32_t max_iters, uint32_t *out) {
    for (uint64_t i = 0; i < img_size; ++i) {
        for (uint64_t j = 0; j < img_size; ++j) {
            float cx = (float(j) / float(img_size)) * 2.5f - 2.0f;
            float cy = (float(i) / float(img_size)) * 2.5f - 1.25f;
            float x2 = 0.0f;
            float y2 = 0.0f;
            float w = 0.0f;
            uint32_t iters = 0;
            while (x2 + y2 <= 4.0f && iters < max_iters) {
                float x = x2 - y2 + cx;
                float y = w - x2 - y2 + cy;
                x2 = x * x;
                y2 = y * y;
                float z = x + y;
                w = z * z;
                ++iters;
            }
            out[i * img_size + j] = iters;
        }
    }
}

This is the reference as the starter has it in both Lab 1 files, with its comments left out. It takes img_size and max_iters, two 32-bit whole numbers, and out, the address in memory where the answers go, one 32-bit whole number after another. The outer for loop gives i every value from 0 to img_size - 1 and, for each i, the inner for loop gives j every value from 0 to img_size - 1, so everything inside executes once for every pair (i, j), each pair being one place of the picture. For each place, cx is j divided by img_size, times 2.5, minus 2.0, and cy is i treated the same way but minus 1.25, as 32-bit fractions, which C++ calls floats. Then x2, y2 and w start out as 0 and iters as 0. Before each trip through its braces, the while loop tests whether x2 + y2 is at most 4 and iters is below max_iters, and makes the trip only when both hold. In the trip, x becomes x2 minus y2 plus cx; y becomes w minus x2, minus y2, plus cy; x2 becomes x times x and y2 becomes y times y; z becomes x plus y; w becomes z times z; and iters goes up by 1. Once the while loop is left, iters is stored in out at entry i times img_size plus j.

Call one trip through the braces of the while loop a repetition, so iters counts the repetitions at a place. Nothing inside the while loop reads another place's values, so every place can be computed on its own.

Reading the GPU starter's empty kernel and launch function

__global__ void mandelbrot_gpu_scalar(
    uint32_t img_size,
    uint32_t max_iters,
    uint32_t *out /* pointer to GPU memory */
) {
    /* your (GPU) code here... */
}

void launch_mandelbrot_gpu_scalar(
    uint32_t img_size,
    uint32_t max_iters,
    uint32_t *out /* pointer to GPU memory */
) {
    /* your (CPU) code here... */
}

__global__ marks mandelbrot_gpu_scalar as a kernel. It receives img_size, max_iters and out, which the comment says is an address in the graphics card's memory, and its body is left for you. launch_mandelbrot_gpu_scalar is an ordinary function that executes on the CPU and receives the same three values; its body is left for you too, and it is meant to start the kernel.

A kernel is started from the CPU with kernel<<<B, T>>>(arguments), which, as NVIDIA's CUDA programming guide defines it, starts B blocks of T threads each, a thread being one execution of the kernel's instructions from its beginning; every thread executes the whole kernel. The GPU file's main uses the launch function like this:

uint32_t *result_device;
CUDA_CHECK(cudaMalloc(&result_device, img_size * img_size * sizeof(uint32_t)));
if (impl == SCALAR || impl == ALL) {
    CUDA_CHECK(cudaMemset(result_device, 0, img_size * img_size * sizeof(uint32_t)));
    BENCHPRESS(launch_mandelbrot_gpu_scalar, img_size, max_iters, result_device);
    CUDA_CHECK(cudaMemcpy(
        result_host.data(),
        result_device,
        img_size * img_size * sizeof(uint32_t),
        cudaMemcpyDeviceToHost));
    dump_image("out/mandelbrot_gpu_scalar.bmp", img_size, max_iters, result_host);
    std::cout << "  Correctness: average output difference from reference = "
              << difference(img_size, max_iters, result_host, ref_result)
              << std::endl;
}

Earlier in the same file, main computes the reference into ref_result on the CPU. It then reserves img_size times img_size 32-bit whole numbers in the graphics card's memory with cudaMalloc and keeps their address in result_device. For the scalar version it sets that memory to 0 with cudaMemset and times launch_mandelbrot_gpu_scalar with BENCHPRESS, defined in the same file, which over 5 measurements calls the launch function 3 times, waits with cudaDeviceSynchronize until the GPU has finished, and prints the smallest measurement divided by 3, in milliseconds. The graphics card's memory is separate from the CPU's, as NVIDIA's CUDA programming guide describes the two, so main then copies it into result_host with cudaMemcpy, writes it as a picture, and prints the average output difference, which the function difference, in the same file, computes as the sum over every place of the gap between result_host and ref_result, divided by img_size times img_size times max_iters.

What you write follows from those pieces. The kernel's body is the reference's body unchanged: both for loops, cx and cy, the while loop and the store into out at entry i times img_size plus j. The launch function starts the kernel with <<<1, 1>>>, 1 block of 1 thread, handing on its three inputs.

nvcc -O3 -arch=sm_75 -std=c++17 mandelbrot_gpu.cu -o mandelbrot_gpu
./mandelbrot_gpu -i scalar

nvcc compiles the CUDA file with full optimization for compute capability 7.5, which is the GTX 1650's, as 2017 C++, into the program mandelbrot_gpu; put your own GPU's compute capability in place of 75. ./mandelbrot_gpu -i scalar computes the reference on the CPU and, since the file's option reader, ParseArgsAndMakeSpec, turns -i scalar into impl = SCALAR, times only the scalar GPU version.

Write the average output difference printed for mandelbrot_gpu_scalar. Computed with the reference's own arithmetic, the counts of the default picture add up to 16,274,722; work out what the program prints when the kernel writes nothing, 16,274,722 / (256 * 256 * 1000), and say what a value between that and 0 would mean.

CHECK

A correct port prints exactly 0. A kernel that writes nothing leaves the 0 that cudaMemset put everywhere, so every gap is the reference's own count and the program prints 16,274,722 / 65,536,000 = 0.2483: the launch is missing, or the kernel never executed.

A value between 0 and 0.2483 means some places are wrong, so the kernel's body differs from the reference somewhere.

A difference of that kind is easy to type. Computed with C++'s rules for mixing 32-bit and 64-bit fractions, writing 2.5 instead of 2.5f in cx and cy changes nothing at the default size, since j / 256 and i / 256 times 2.5 come out exact in 32 bits for every j and i. ParseArgsAndMakeSpec takes the size after -r as img_size, and at -r 384 the same change alters 134 of the 384 values of cx and 83 of the 384 values of cy, and the counts at 372 of the 384 * 384 = 147,456 places, and the program prints 0.000228.

Timing one GPU thread against one CPU core

Measured on the laptop for the default picture, the reference on one CPU core took 61.6 ms and the GPU version with 1 block of 1 thread took 403.435 ms. Both make the same 16,274,722 repetitions, since the kernel's body is the reference's.

Divide 403.435 by 61.6. Then divide each time by the 16,274,722 repetitions to get the time of one repetition on each chip.

CHECK 
403.435 / 61.6 = 6.55 times longer on one GPU thread
CPU: 61.6 ms / 16,274,722    = 3.79 ns per repetition
GPU: 403.435 ms / 16,274,722 = 24.79 ns per repetition

Following the operations that wait for each other through one repetition

Inside a repetition, some operations need the value of an operation before them. Call a list of operations in which each one waits for the previous one a chain.

Begin at w, made by the last operation of one repetition, and follow it into the next repetition: the new y needs w minus x2, minus y2, plus cy; z needs x plus y; and the new w needs z times z. Count the operations from one w to the next. Then count the operations from one x2 to the next, through x = x2 - y2 + cx and x2 = x * x, and from one y2 to the next, through y2 = y * y and the subtraction of y2 and addition of cy inside the new y.

CHECK

From one w to the next: w - x2, then - y2, then + cy make y, 3 operations; z = x + y, 1; w = z * z, 1; so 5. From one x2 to the next: x2 - y2, + cx, x * x, so 3. From one y2 to the next: y * y, then - y2 and + cy inside the next y, so 3. The longest chain that repeats from one repetition into the next is the 5 through w.

Published figures give the wait at each operation of that chain, in cycles, a cycle being one tick of a chip's clock. For the laptop's CPU, whose cores are of the design AMD's specification calls Zen 2, Agner Fog's instruction tables give a wait of 3 cycles for a float add or multiply that needs the previous result, and AMD's specification of the Ryzen 5 4600H gives a busy core up to 4.0 billion cycles per second. On the GTX 1650 the Lab 2 prelab timed a single chain of 64 multiply-adds, each one instruction computing a times b plus c, at 281 cycles and a chain of 256 at 1055, so each extra multiply-add waited (1055 - 281) / 192 = 4.03 cycles, and NVIDIA's Turing tuning guide gives the same 4 cycles for the float add and multiply. NVIDIA gives the GTX 1650 laptop GPU a boost clock between 1,125 and 1,560 MHz, depending on the laptop; the clock during these measurements was not recorded, so this lesson works at both ends of that range, and nvidia-smi -q -d CLOCK reads yours.

Work out the chain's time per repetition on each chip, 5 * 3 cycles at 4.0 billion per second, and 5 * 4 cycles at 1.125 and at 1.56 billion per second, and set each beside the measured 3.79 and 24.79 ns. How much of each chip's time does the chain explain?

CHECK 
CPU: 15 cycles / 4.0e9 per second = 3.75 ns,  measured 3.79 ns
GPU: 20 cycles / 1.125e9 per second = 17.8 ns,  20 cycles / 1.56e9 per second = 12.8 ns,  measured 24.79 ns

The chain explains nearly all of the CPU's time, 3.75 of 3.79 ns, and between 12.8 / 24.79 = 52 and 17.8 / 24.79 = 72 percent of the GPU's.

Agner Fog's microarchitecture manual describes Zen 2 cores as predicting which way a branch goes and executing ahead, out of order, so on the CPU the comparison with 4 and the count can overlap the chain. NVIDIA's CUDA programming guide says that a GPU thread's instructions are issued in order, with no branch prediction, so on the GPU the comparison and the branch add to the chain. This page measures neither.

Counting the arithmetic circuits one thread can use

NVIDIA's specification of the GTX 1650 lists 896 circuits that each do a float multiply-add for one thread, which it calls CUDA cores. Each float operation of a thread is done by one such circuit, and a single thread issues its instructions in order, one after another, so it keeps at most 1 of the 896 busy at a time and the others have nothing to do.

Gathering what one GPU thread showed

A single GPU thread took 403.435 ms against 61.6 ms on one CPU core, 6.55 times longer; a repetition took 24.79 ns against 3.79 ns; the 5-operation chain explains 3.75 of the CPU's 3.79 ns and 12.8 to 17.8 of the GPU's 24.79 ns across NVIDIA's clock range; and the thread keeps at most 1 of the GTX 1650's 896 float circuits busy.

Write one sentence that answers the handout's first question: what makes one GPU thread slower than one CPU core, and what does that say about how a GPU has to be used?

CHECK

A single GPU thread is a slow, simple processor, with a lower clock, no working ahead past the loop's branch, the same 5-operation chain to wait through and at most 1 of 896 float circuits; a GPU is fast only when many threads keep those circuits busy at once.

The reading "GPUs are slower than CPUs" fails, because the comparison sets 1 of 896 circuits against a whole core and says nothing about the chip.

The Fall 2025 handout's first question asks how the scalar GPU version's time compares with the scalar CPU version's and what might explain each, and the ratio of 6.55, the two times per repetition and the chain on each chip answer it.

An average output difference of about 0.248 with a tiny time means the launch is missing or the kernel never executed. A difference between 0 and 0.248 means the kernel's body differs from the reference somewhere. A GPU time far from 403 ms means a different GPU or clock, and the comparison that still holds is your time per repetition against the chain at your own clock.

A graphics card is not one fast processor but hundreds of simple circuits that are fast together, and given to a single one of its threads, the whole picture took 6.55 times longer than on one ordinary CPU core. Moving work onto a GPU without splitting it into many independent pieces makes it slower, and the hardware alone buys nothing.

The time asked for at the start is more: 403.435 ms, 6.55 times the 61.6 ms of one CPU core.

The CPU's time per repetition matches its chain within about 1 percent, 3.75 against 3.79 ns, and the GPU thread's does not, 12.8 to 17.8 against 24.79 ns. clock64(), a CUDA function, returns the GPU's cycle counter. Name measurements that would tell whether the missing part on the GPU comes from the clock or from the instructions outside the chain.

CHECK

Fix the clock first: read it during the measurement with nvidia-smi -q -d CLOCK. Then count cycles per repetition directly with clock64(): read it before and after the while loop for one place with a known count, 1000 for example, and divide by that count. Cycles above 20 per repetition come from instructions outside the chain, while a clock at the low end of the range would show in the first measurement and not in the second.
