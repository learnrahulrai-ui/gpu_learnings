Lesson 3. Vector code on the CPU: 8 places per instruction

This lesson covers Lab 1, part 2, on the CPU, where you write mandelbrot_cpu_vector. It needs a CPU with AVX2, or AVX-512 as the handout assumes. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

The second part of Lab 1 asks for the same picture computed with explicit vector instructions, each acting on several places at once. The Fall 2025 handout uses AVX-512, 16 floats per instruction; the laptop has AVX2, 8 floats, so everything below is written for 8, and with AVX-512 every 8 becomes 16. A direct translation of the reference meets two problems: the reference computes cx from one j, but a vector needs 8 different values of cx at once, and each place leaves the while loop after its own number of repetitions while every instruction acts on all 8. How do 8 places with different counts share one loop, and what does the sharing cost?

The second problem is the one that stops most people, and it was put this way at this step:

"SIMD does not even understand while loop. So where is the connection between this while loop and SIMD?" / "How can I tell SIMD that don't update 8, 9 but only update 10, 11, 12?" / "Suppose one square finishes after two repetitions, but another needs five. There is no way to know." / "It just happens that the mask contains negative numbers, right?"

Write a guess. With 8 places per instruction, what speedup over the reference on the same core do you expect: 8, a little under 8, or much less?

All 8 values of cx come from one number plus the offsets 0 to 7

In C++, as Intel's intrinsics guide documents them, a __m256 variable holds 8 floats at index 0 to 7, _mm256_set1_ps(a) puts a at all 8 indexes, and _mm256_set_ps(e7, e6, e5, e4, e3, e2, e1, e0) takes its arguments from index 7 down to index 0. Adding, subtracting and multiplying act index by index, and _mm256_fmadd_ps(a, b, c), a fused multiply-add, computes a times b plus c at each index in one instruction. The vector code takes 8 neighbours at once, the same i and j, j + 1, up to j + 7, with j a multiple of 8, while the reference computes cx = j / img_size x 2.5 - 2.0 for each j separately.

Split cx at j + k into the cx of j plus k times a step, and write the step. With img_size = 256 work out the step, then cx at k = 0 and at k = 7 for j = 64.

CHECK 
cx(j + k) = (j / img_size x 2.5 - 2.0) + k x (2.5 / img_size)
step = 2.5 / 256 = 0.009765625
j = 64: k = 0 -> -1.375;  k = 7 -> -1.375 + 7 x 0.009765625 = -1.306640625

So one vector of offsets 0 to 7, times the step, plus the cx of j, gives all 8 values of cx in one instruction, _mm256_fmadd_ps(offsets, step, cx of j).

__m256 offsets = _mm256_set_ps(7, 6, 5, 4, 3, 2, 1, 0);
float  dx      = 2.5f / float(img_size);
for (uint64_t i = 0; i < img_size; ++i) {
    float  cy     = (float(i) / float(img_size)) * 2.5f - 1.25f;
    __m256 cy_vec = _mm256_set1_ps(cy);
    for (uint64_t j = 0; j < img_size; j += 8) {
        float  cx     = (float(j) / float(img_size)) * 2.5f - 2.0f;
        __m256 cx_vec = _mm256_fmadd_ps(offsets, _mm256_set1_ps(dx), _mm256_set1_ps(cx));
        /* the while loop works on cx_vec, cy_vec here */
    }
}

Read in English, the first line puts 0 at index 0 up to 7 at index 7, since _mm256_set_ps takes index 7 first; the second computes the step 2.5 / img_size once. For each i, cy is computed once as in the reference and copied to all 8 indexes. For each j in steps of 8, cx is computed for j alone, and the fmadd line makes the 8 values offset times step plus that cx. The comment marks where the while loop works on these 8 values.

Which index holds offset 0 in that code? If the offsets were written _mm256_set_ps(0, 1, 2, 3, 4, 5, 6, 7) instead, which offset would index 0 hold, and how would each block of 8 results be stored?

CHECK

Written 7, 6, 5, 4, 3, 2, 1, 0, offset 0 sits at index 0. Written 0, 1, ..., 7, index 0 holds 7, so every block of 8 is stored mirror-reversed; _mm256_setr_ps takes its arguments in index order instead.

Subtracting the compare result adds 1, because all ones is -1

__m256  four      = _mm256_set1_ps(4.0f);
__m256i iters_vec = _mm256_setzero_si256();
uint32_t iter = 0;
while (iter < max_iters) {
    __m256 mask = _mm256_cmp_ps(_mm256_add_ps(x2_vec, y2_vec), four, _CMP_LE_OQ);
    if (_mm256_testz_ps(mask, mask)) break;
    iters_vec = _mm256_sub_epi32(iters_vec, _mm256_castps_si256(mask));
    /* lines A to F, each one an _mm256_..._ps instruction */
    ++iter;
}

Read in English, the first two lines make a vector of 8 fours and 8 counters at 0, and iter counts repetitions of the whole loop. Each repetition first adds x2 and y2 at each index and compares the sum with 4, putting 32 bits all 1 where it is at most 4 and all 0 elsewhere, which is mask. If all 256 bits of mask are 0, the loop is left at once. Otherwise mask, read as 8 whole numbers, is subtracted from the 8 counters, lines A to F are done with vector instructions, and iter goes up by 1.

_mm256_testz_ps(mask, mask) returns 1 only when every bit of mask is 0, and _mm256_sub_epi32 subtracts index by index, reading the bits as whole numbers. Nothing in the loop asks an index whether it has finished.

Add 1 in binary to the 32-bit integer whose bits are all 1, and write what is left in 32 bits. What is all ones as a signed integer, and so what does subtracting mask do at an index that is all ones, and at one that is all zeros?

CHECK 
  11111111 11111111 11111111 11111111
+                                   1
= 1 00000000 00000000 00000000 00000000   (the leading 1 does not fit)

The 32 bits left are all 0, so all ones is the integer that becomes 0 when 1 is added, which is -1. At an all-ones index, iters - (-1) = iters + 1; at an all-zeros index, iters - 0 = iters. Each index counts itself, with no if.

Take a real block, i = 40 and j = 208 to 215, whose scalar counts are 12, 8, 7, 6, 6, 6, 5 and 5. An index with count c has mask all ones before repetitions 1 to c and all zeros after, because a point farther than 2 from (0, 0) never comes back. How many repetitions does the vector loop make, and what does the counter vector hold after repetition 7?

CHECK

The test returns 1 before repetition 13, since index 0, with 12, is the last one inside, so the loop makes 12 repetitions. After repetition 7 the counters read 7 7 7 6 6 6 5 5, and after repetition 12 they read 12 8 7 6 6 6 5 5, the scalar counts.

Writing mandelbrot_cpu_vector, and the exact 0 it must print

The function loops over every i, and over j in steps of 8; builds cx as above and cy with _mm256_set1_ps; begins x2, y2 and w at zero and the counters at zero; repeats lines A to F with _ps instructions inside the loop above; and stores the 8 counts with _mm256_storeu_si256 at out + i * img_size + j. The aligned store, _mm256_store_si256, needs an address that is a multiple of 32 bytes, which the starter's out is not guaranteed to be, and it crashes with a segmentation fault where the unaligned one works.

Compile as in the setup lesson, with -march=native for AVX2, execute ./mandelbrot_cpu -i vector, and write the printed difference.

CHECK

A correct version prints exactly 0. About 0.248 means nothing was stored, usually a missing store line. A small value that is not 0 means some indexes are wrong, most often the offsets order above, or a loop that stops before the last index has left.

A version that is correct at img_size 256 and wrong at a size such as 384 has met rounding: 2.5 / img_size is exact in a float only when img_size is a power of 2, so cx built by steps rounds differently from the reference's division at other sizes.

Neighbours make 8 places per instruction worth 7.07 times, and shuffled places 2.23

Measured on the laptop on one core, the reference took 61.6 ms and the AVX2 version 8.71 ms. An index doing one repetition will be called an index-repetition here; each repetition of the vector loop costs 8 of them, useful or not, and the useful ones add up to the scalar counts. For the block i = 22, j = 184 to 191, with counts 7, 8, 10, 15, 154, 1000, 13 and 10, the loop needs 1000 repetitions. Over all 8,192 blocks of 8 neighbours in the picture, 16,274,722 of 18,321,656 index-repetitions are useful, and with the places shuffled at random into blocks of 8, 27.9 percent are.

Work out the useful share of the i = 22 block and of the whole picture. If only index-repetitions cost time, AVX2 is faster than the reference by 8 times the useful share: work that out with neighbours and with shuffled places, and set it beside the measured 61.6 / 8.71.

CHECK 
i = 22 block:   (7 + 8 + 10 + 15 + 154 + 1000 + 13 + 10) / 8000 = 1217 / 8000 = 15.2 percent
whole picture:  16,274,722 / 18,321,656 = 88.8 percent
predicted:      8 x 0.888 = 7.11 with neighbours;  8 x 0.279 = 2.23 shuffled
measured:       61.6 / 8.71 = 7.07

Similar neighbours, not the instructions, decide the speedup

Gathered together, the offsets have to go in reverse into _mm256_set_ps; each index counts itself through the mask; one block can waste 85 percent of its index-repetitions while the whole picture wastes 11; the prediction from useful index-repetitions is 7.11 against 7.07 measured; and the same instructions on shuffled places predict 2.23.

Write one sentence on what decides the speedup of 8 places per instruction.

CHECK

Neighbouring places usually need similar numbers of repetitions, so most blocks of 8 finish together and waste little, and only blocks on the edge of the set mix 1000 with small counts. The 7 times comes from that feature of the picture, not from the instructions: shuffled blocks give 2.23 with the same code.

The reading "8 floats per instruction, so 8 times minus overhead" fails, because the same code predicts 2.23 when the places in each block are not neighbours.

The handout's second question asks how you set up cx and cy, how you handled places in one vector that need different numbers of repetitions, and how the vector version compares with the scalar ones; the offsets and the step answer the first part, the mask that counts each index by itself the second, and 7.07 measured against 7.11 predicted the third. A loop that never ends, or always takes max_iters repetitions, has its test on the wrong mask or compares no repetition counter with max_iters.

Without code, processing 8 places with one instruction is close to 8 times faster only because neighbouring places of this picture need similar amounts of work; mixed with unlike places, the same instructions gain barely 2 times, so the gain from doing several things at once depends on how alike those things are, and a gain measured on friendly data does not carry over to mixed data.

The guess at the top has its answer: a little under 8, 7.07 times, against 7.11 predicted from the useful share of index-repetitions.

A harder question to finish with. Before writing any code, how would you predict the AVX-512 version's speedup on the course machine, 16 places per instruction, from data you already have?

CHECK

Repeat the count with blocks of 16 neighbours: the useful share is the sum of the counts divided by 16 times the sum, over blocks, of the largest count in each block, and the predicted speedup is 16 times that share. Blocks of 16 mix more unlike places than blocks of 8, so the share falls below 88.8 percent and the speedup below 16 x 0.888 = 14.2. Compute it from the scalar counts before measuring.
