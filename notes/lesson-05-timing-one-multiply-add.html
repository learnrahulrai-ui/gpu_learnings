Lesson 5. Timing one multiply-add

This lesson covers part 0 of Lab 2, the prelab file fma_latency.cu, whose three timed kernels you fill. It needs an NVIDIA GPU and cuobjdump, which comes with the CUDA toolkit. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

Lab 2 begins with a prelab that measures one number: how many cycles a multiply-add takes on the GPU when it needs the result of the one before. The starter file fma_latency.cu provides a clock read and three kernels to fill, one chain of multiply-adds, two chains interleaved, and two chains written one after the other. The result depends on what the source code does not show: where the compiler moves an add, which constant silently becomes exactly 1.0, and whether two loops written one after the other stay that way. What lies between the two clock reads, and which number from them can be trusted?

Facing the starter for the first time, the question was what to write at all:

"Okay, now I am seeing this data type, start and clock time ... I see a thread fence ... What code I should write and what should I think to finish this function?" / "I am confused with all these things, right? So can you clearly tell me what line of code I have to write and why?"

Write a guess. On the GTX 1650, how many cycles go by from one multiply-add to the next when each needs the previous result: 1, 4 or 20?

A pair of clock reads times whatever the compiler puts between them

#define clock_cycle() \
    ({ \
        unsigned long long ret; \
        asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret)); \
        ret; \
    })

Read in English, the macro defines a shorthand named clock_cycle(), and the backslash at the end of each line continues the definition onto the next. It declares a 64-bit variable ret, inserts one GPU instruction by hand, mov.u64, that copies the chip's cycle counter %clock64 into ret, and hands ret back as the value of the whole expression; volatile tells the compiler not to delete the instruction, and nothing is listed after the second colon, so the instruction takes no input.

%clock64 is, as NVIDIA's PTX documentation defines it, a 64-bit counter inside the GPU chip that goes up by 1 at every tick of the GPU's clock, and a tick is a cycle. A kernel reads it before and after the timed code, and main prints the difference, as in Latency of fma_latency code snippet = 281 cycles. The prelab, in the Fall 2025 handout, fills three kernels, each launched with <<<1, 1>>>: fma_latency with one chain of multiply-adds, fma_latency_interleaved with two chains whose steps alternate, and fma_latency_no_interleave with two chains written one after the other, and asks for the cycles per multiply-add, an FFMA instruction in the machine listing, in each.

#pragma unroll
for (int i = 0; i < 64; ++i)
    x = x * 1.0000001f + 0.00000001f;

Read in English, the pragma tells the compiler to write the loop out as 64 separate copies of its line, and each copy multiplies x by 1.0000001, adds 0.00000001 and puts the result back into x, which the next copy reads.

In the IEEE 754 32-bit format, a float between 1 and 2 is 1.0 plus a multiple of 2 to the power -23, 0.00000011920929, and a typed constant becomes the nearest such value. Which of 1.00000001f, 1.0000001f and 1.0000002f becomes exactly 1.0, and why does that matter for a timed chain?

CHECK 
half the spacing = 0.0000000596
1.00000001f: 0.00000001 is below half the spacing -> exactly 1.0 (0x3f800000)
1.0000001f  -> 1 + 1 step  (0x3f800001)
1.0000002f  -> 1 + 2 steps (0x3f800002)

A chain that multiplies by exactly 1.0 may be simplified by the compiler, so the timed code would not be the chain that was written.

data_type x = *n;                  // data_type is float (using data_type = float;)
__threadfence();
x = x + 3;
start_time = clock_cycle();
#pragma unroll
for (int i = 0; i < 64; ++i)
    x = x * 1.0000001f + 0.00000001f;
end_time = clock_cycle();

Read in English, the kernel copies *n from the graphics card's memory into x, a float, since data_type is float, waits until earlier memory operations are visible with __threadfence, adds 3 to x, reads the clock into start_time, does the 64 copies of the multiply-add, and reads the clock into end_time.

Here *n lives in DRAM, the memory chips outside the GPU chip, so x = *n becomes a load instruction, LDG in the listing. The chip begins the next instruction without waiting for the load, and an instruction that reads the loaded register is held until the value arrives, as the 2019 microbenchmark study of Jia and others, Dissecting the NVIDIA Turing T4 GPU via Microbenchmarking, describes; so the add, which the starter file's own comment says is there to make sure the read of *n is done, exists to pay the wait for the load before the first clock read.

In the interleaved version x and y both came from that load, and x = x + 3.0f; y = y + 4.0f; sat above the first clock read. The listing showed the clock read, CS2R at address 0060, before both adds, FADD at 0080 and 0090. Which waits fall inside the timed window, what in the clock macro allowed the move, and if a fixed clock read lists only x as its input, which add may still move inside?

CHECK

The wait for the DRAM load and both FADDs fall inside. The macro lists no input, so nothing ties the clock read to the adds. With only x listed, the add on y is tied to nothing and may still move after the read, which is what the report on the laptop's listing showed.

#define clock_cycle_dep2(a, b) \
    ({ \
        unsigned long long ret; \
        asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret) : "f"(a), "f"(b)); \
        ret; \
    })
start_time = clock_cycle_dep2(x, y);

Read in English, this version of the clock read is the same copy of the counter with a and b listed after the second colon as float inputs, so it cannot begin before a and b have values; the last line uses it to pin the start read to x and y. The starter has no such macro, so this is an addition of your own.

An end read with no input: can it begin before the last FFMA of the chain has its value? If so, is the printed number too small or too large, and what should the end read take as inputs?

CHECK

It can, because it reads no register that the last FFMA writes, so the wait for the last value is left out and the number is too small. The end read takes the chain's final values as inputs, end_time = clock_cycle_dep2(x, y).

Reading the machine listing settles what was timed

nvcc -O3 -arch=sm_75 -std=c++17 fma_latency.cu -o fma_latency
./fma_latency
nvcc -O3 -arch=sm_75 -cubin fma_latency.cu -o fma_latency.cubin
cuobjdump --dump-sass fma_latency.cubin | grep -e CS2R -e LDG -e FADD -e FFMA

The first line compiles the prelab file for compute capability 7.5 and the second executes it, each kernel printing its cycles. The third compiles only the GPU part, into a file of machine code, and the fourth prints its machine instructions, keeping only the clock reads, the loads, the adds and the multiply-adds.

In your listing of fma_latency, count the FFMAs between the two CS2R clock reads and the FADDs between them, and write what a correct single chain of 64 should show.

CHECK

A correct chain shows 64 FFMAs and no FADD between the reads. More FADDs inside means the start read is not pinned; fewer FFMAs means the compiler simplified the chain, often because a constant became 1.0.

281 / 64 = 4.39 spreads a fixed part over 64 operations, and subtraction gives 4

The laptop measured six numbers. A single chain printed 281 cycles for 64 FFMAs and 1055 for 256, the second from a copy-paste bug that turned two chains into one long one. With two chains it printed 295 cycles for 128 FFMAs in all and 551 for 256, and with four chains 519 for 256 and 1031 for 512.

Divide 281 by 64. Then subtract two lengths of the same kind instead, for one chain (1055 - 281) / (256 - 64), for two chains (551 - 295) / (256 - 128), and for four chains (1031 - 519) / (512 - 256).

CHECK 
281 / 64 = 4.39, the fixed part spread over 64 FFMAs
one chain:   774 / 192 = 4.03 -> 4 cycles from one FFMA to the next
two chains:  256 / 128 = 2
four chains: 512 / 256 = 2

The 2 has two possible explanations. In the first, an FFMA can begin every cycle, so k chains give 4 / k cycles, never below 1; in the second, an FFMA keeps the arithmetic circuits busy for 2 cycles, never below 2. Write what each predicts for four chains and set it beside the measurement. Then use the layout of an SM, one of the identical blocks of hardware a Turing chip is built from, as NVIDIA's Turing tuning guide publishes it, 64 float circuits and 4 schedulers, the circuits that pick which instruction begins, to work out the circuits per scheduler and the cycles needed to feed 32 threads through them.

CHECK

The first guess predicts 4 / 4 = 1 and the second 2; the measurement is 2, so the first fails. Each scheduler has 64 / 4 = 16 circuits, and 32 threads through 16 circuits take 32 / 16 = 2 cycles. With two chains both guesses give 2, so only the four-chain kernel tells them apart.

The outside part of a measurement is the cycles its FFMAs do not explain: with N FFMAs at r cycles each, the last begins (N - 1) x r cycles after the first, so the outside part is the measurement minus (N - 1) x r. Work it out for all six measurements.

CHECK 
one chain, 64:     281 -  63 x 4 = 29
one chain, 256:   1055 - 255 x 4 = 35
two chains, 128:   295 - 127 x 2 = 41
two chains, 256:   551 - 255 x 2 = 41
four chains, 256:  519 - 255 x 2 = 9
four chains, 512: 1031 - 511 x 2 = 9

The same kernel gives the same outside part, 41 and 41, 9 and 9, while different kernels give different parts, 29 against 35; that is why the one-chain answer came out 4.03 and not 4.00, since (35 - 29) / 192 = 0.03.

After the bug was fixed, fma_latency_no_interleave had all 128 FFMAs of x, then all 128 of y, in the source. It printed 551 cycles, and its listing alternated the registers of x and y, while the chip begins instructions in listing order. Who interleaved the chains, and does the no-interleave version show the same cycles as the interleaved one?

CHECK

The compiler reordered the two independent loops into one alternating stream, so both versions print 551 with the same listing: the source order of independent work does not survive -O3.

A cycle count holds up only with pinned reads, a checked listing and two lengths of one kernel

Gathered together, a constant can silently become 1.0; an add placed above the timer can sit inside it in the listing; the listing is the only judge of what was timed; dividing one measurement gives 4.39 where subtraction gives 4.03 and 2; the four-chain kernel rules out one guess; the outside parts read 29, 35, 41 and 9; and the compiler interleaved the chains it was given one after the other.

Write one sentence on how to get one trustworthy cycle count from a GPU clock.

CHECK

Pin both clock reads to the chain's values, check in the machine listing that exactly the chain sits between them and that no constant became 1.0, then subtract two lengths of the same kernel; never divide one measurement, and never subtract two different kernels.

The reading "the clock reads cost the same everywhere, so any two measurements can be subtracted" fails on the outside parts, which came out 29, 35, 41 and 9.

The prelab's first question, the cycles of an FFMA that needs the previous one, is answered by the subtraction, 4. The second, what two interleaved chains show and whether it contradicts the first, is answered by the 2 cycles per FFMA, with no contradiction, since 4 is a wait and 2 is the time to begin. The third, whether the no-interleave version shows the same cycles, is answered by the compiler's reordering. Cycles that barely change when the chain doubles mean a simplified chain, a constant that became 1.0 or two chains with the same constants merged into one; cycles that change when setup lines move mean a clock read with no inputs.

Without code, a cycle counter inside a chip measures whatever the compiler placed between its two readings, which is not always what the source code shows, so the method that holds up is to check the machine instructions, then time the same thing at two lengths and subtract. A measurement taken without checking what was measured can be wrong by a large factor while looking precise to three digits.

The guess at the top has its answer: 4 cycles, by subtraction, (1055 - 281) / (256 - 64) = 4.03, and 4.00 exactly within one kernel at three lengths, 281, 537 and 793 cycles, as reported in the chat.

A harder question to finish with. The outside part was 41 cycles with two chains and 9 with four. Propose a reason, and a measurement that would test it.

CHECK

A guess, not a measured fact: with more chains, more of the final multiply-adds are under way together, so the wait after the last one begins overlaps more of the others. Measuring 1, 2, 3 and 4 chains at two lengths each and computing the outside part of each shows whether it shrinks steadily with the number of chains.

The lab pages what sits between the clock reads and cycles per FFMA work these numbers out at length, and the notes on clock reads, subtracting two lengths and independent chains hold the short versions.
