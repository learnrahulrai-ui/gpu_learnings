The story

Lab 2 begins with a prelab that measures one number: how many cycles a multiply-add takes on the GPU when it needs the result of the one before. The starter file fma_latency.cu provides a clock read and three kernels to fill: one chain of multiply-adds, two chains interleaved, and two chains written one after the other.

The learner wrote the kernels and got numbers, then found that the numbers depended on things the source code did not show: where the compiler had moved an add, which constant had silently become exactly 1.0, and whether two loops written one after the other stayed that way.

What exactly lies between the two clock reads, and how do you get one honest number out of them?

Guess first

On the GTX 1650, guess the cycles from one multiply-add to the next when each needs the previous result: 1, 4 or 20?

Work it out

L01 The starter's clock read in fma_latency.cu, copied from page 09: from: Lab 2 starter code

#define clock_cycle() \
    ({ \
        unsigned long long ret; \
        asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret)); \
        ret; \
    })

Read the code in English, line by line

  1. #define clock_cycle() \Define a shorthand named clock_cycle(). The backslash at the end continues the definition on the next line.
  2. ({ \Begin a block whose last value becomes the value of the shorthand.
  3. unsigned long long ret; \Make a 64-bit whole number named ret.
  4. asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret)); \Insert one GPU instruction by hand: copy the 64-bit clock counter into ret. volatile tells the compiler not to delete it. Nothing is listed as an input.
  5. ret; \The value of the block is ret.
  6. })End of the block.

L02 %clock64 is a 64-bit counter inside the GPU chip that goes up by 1 at every tick of the GPU clock; a tick is a cycle. A kernel reads it before and after the timed code, and main prints the difference, for example Latency of fma_latency code snippet = 281 cycles. from: L01, PTX definition, your output

L03 The prelab (Fall 2025 handout): fill three kernels, each launched with <<<1, 1>>>: fma_latency (one chain of multiply-adds), fma_latency_interleaved (two chains whose steps alternate) and fma_latency_no_interleave (two chains, one written after the other); report the cycles per multiply-add, an FFMA instruction in the machine listing, for each. from: Lab 2 handout (Fall 2025), Lab 2 starter code

L04 The learner's timed loop, copied from page 10: from: your code

#pragma unroll
for (int i = 0; i < 64; ++i)
    x = x * 1.0000001f + 0.00000001f;

Read the code in English, line by line

  1. #pragma unrollTell the compiler to write the loop out as separate copies of its line instead of a loop that jumps back.
  2. for (int i = 0; i < 64; ++i)Repeat the next line 64 times.
  3. x = x * 1.0000001f + 0.00000001f;Multiply x by 1.0000001, add 0.00000001, and put the result back into x. The next copy uses this new x.

L05 DO A float holds 1.0 plus multiples of 2 to the power -23 = 0.00000011920929 between 1 and 2, and a typed constant becomes the nearest such value. Which of 1.00000001f, 1.0000001f and 1.0000002f becomes exactly 1.0? ____ . Why does that matter for a timed chain? ____ . from: IEEE 754 float32

CHECK 
half the spacing = 0.0000000596; 0.00000001 is below it -> 1.00000001f becomes exactly 1.0
1.0000001f = 1 + 1 step (0x3f800001); 1.0000002f = 1 + 2 steps (0x3f800002)
A chain that multiplies by exactly 1.0 may be simplified by the compiler, so the timed code is
not the chain you wrote.

L06 The learner's fma_latency kernel, the lines that matter, copied from page 09: from: your code

data_type x = *n;                  // data_type is float (using data_type = float;)
__threadfence();
x = x + 3;
start_time = clock_cycle();
#pragma unroll
for (int i = 0; i < 64; ++i)
    x = x * 1.0000001f + 0.00000001f;
end_time = clock_cycle();

Read the code in English, line by line

  1. data_type x = *n; // data_type is float (using data_type = float;)Read the fraction stored at address n in the graphics card's memory and keep it in x. data_type is another name for float, set by the line using data_type = float;.
  2. __threadfence();A memory fence. The starter file's own note says it is there to make sure the read of *n is done.
  3. x = x + 3;Add 3 to x.
  4. start_time = clock_cycle();Read the clock counter into start_time.
  5. #pragma unrollTell the compiler to write the loop out as separate copies of its line instead of a loop that jumps back.
  6. for (int i = 0; i < 64; ++i)Repeat the next line 64 times.
  7. x = x * 1.0000001f + 0.00000001f;Multiply x by 1.0000001, add 0.00000001, and put the result back into x. The next copy uses this new x.
  8. end_time = clock_cycle();Read the clock counter into end_time.

L07 Facts: *n lives in DRAM, the memory chips outside the GPU chip, so x = *n becomes a load instruction, LDG in the listing. The chip begins the next instruction without waiting for the load; an instruction that reads the loaded register is held until the value arrives. So x = x + 3 pays the wait before the first clock read; that is its only job. from: L06, Jia et al. 2019, Dissecting the NVIDIA Turing T4 GPU

L09 A clock read with inputs, the form the learner wrote; the starter has none, so this is your own addition: from: your code

#define clock_cycle_dep2(a, b) \
    ({ \
        unsigned long long ret; \

    })
start_time = clock_cycle_dep2(x, y);

Read the code in English, line by line

  1. #define clock_cycle_dep2(a, b) \Define a shorthand named clock_cycle_dep2 that takes two values, a and b.
  2. ({ \Begin a block whose last value becomes the value of the shorthand.
  3. unsigned long long ret; \Make a 64-bit whole number named ret.
  4. asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret) : "f"(a), "f"(b)); \Same clock copy, but after the second colon a and b are listed as float inputs, so the instruction cannot begin before a and b have values.
  5. ret; \The value of the block is ret.
  6. })End of the block.
  7. start_time = clock_cycle_dep2(x, y);Read the clock into start_time, tied to x and y.

When it goes wrong

  • The cycles barely change when you double the chain. The compiler simplified the chain: a constant became exactly 1.0 (L05), or two chains with the same constants were merged into one.
  • The cycles change when you move setup lines. The clock read has no inputs, so setup slid inside the window (L08).
  • 4.39 instead of 4. A single measurement divided by a count (L14).
  • The no-interleave and interleaved kernels print the same number. Correct: the compiler interleaved them for you (L17).

In plain words

A stopwatch inside a chip measures whatever the compiler placed between its two readings, which is not always what the source code shows. The honest method is to check the machine instructions, then time the same thing at two lengths and subtract.

For a manager: a measurement taken without checking what was actually measured can be wrong by a large factor while looking precise to three digits.
