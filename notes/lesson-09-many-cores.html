Lesson 9. Many CPU cores, many SMs

This lesson covers part 2 of Lab 2, where you write mandelbrot_cpu_vector_multicore, mandelbrot_gpu_vector_multicore and its launch, beginning from the ported Lab 2 vector versions. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

Part 2 of Lab 2 spreads the vector version over many cores: one CPU thread per core, and on the GPU one set of 32 threads for each scheduler, the circuit that picks which instruction begins next. Either of two things can go wrong, and neither shows in the time alone. A split can give some places two writers and others none, and a correct split can still give one worker far more of the work, so that the job ends only when that worker does. How do you split a picture whose work is unevenly spread, and how do you know every part of the GPU got its share?

The first surprise at this step was that the part asks for threads at all:

"One question. So in this assignment I have to make threads? I thought I am just extending SIMD." / "Help me recall my working memory is zero."

Write a guess. Split the Lab 2 picture's 1024 values of i between 6 CPU threads in 6 consecutive bands. If time follows the work, is the speedup over one thread about 6, about 5, or about 3?

Bands of i give 4.72 times on 6 threads, and turns give 5.98

Call the worker that writes a given place of out its owner; a split is correct only if every place has exactly one owner. The Fall 2025 handout's CPU, an AMD Ryzen 7 7700, has 8 cores with 2 hardware threads each, and part 2 asks for 8 CPU threads; the laptop's Ryzen 5 4600H has 6 cores with 2 hardware threads each, so 6 CPU threads here.

Cut the 1024 values of i into 6 consecutive bands: divide, round up, and write the bands from [0, 171) to the last one. The repetitions per band, computed from the real Lab 2 counts, are 20,219,285, 20,203,424, 28,346,172, 29,263,472, 19,303,420 and 20,884,049, out of 138,219,822. The job ends with the largest band; work out the speedup.

CHECK 
1024 / 6 = 170.67, rounded up 171
[0,171) [171,342) [342,513) [513,684) [684,855) [855,1024)
138,219,822 / 29,263,472 = 4.72, not 6

Deal the values out in turns instead: owner t takes i = t, t + 6, t + 12, and so on. Which owner gets i = 1023, and why can no value of i have two owners? The repetitions per owner are 23,029,821, 23,043,321, 23,099,034, 23,079,169, 22,974,325 and 22,994,152; work out the speedup.

CHECK

1023 = 170 x 6 + 3, so owner 3 gets it; each i has exactly one remainder when divided by 6, so exactly one owner. The speedup is 138,219,822 / 23,099,034 = 5.98.

A shared description of the work leaves whole lines without an owner

struct Args { uint32_t first; uint32_t step; uint32_t *out; };
Args args[6];
pthread_t tid[6];
for (uint32_t t = 0; t < 6; ++t) {
    args[t] = {t, 6, out};
    pthread_create(&tid[t], nullptr, worker, &args[t]);
}
for (uint32_t t = 0; t < 6; ++t) pthread_join(tid[t], nullptr);

Read in English, the struct describes what one worker needs, the first i it owns, the step to its next i and the address of the picture; args holds 6 such descriptions, one per worker, all alive until this function ends, and tid holds 6 thread handles; for t from 0 to 5 the loop fills worker t's own description with first i t and step 6, and starts a thread with the POSIX threads call pthread_create, executing the function worker on the address of that description; the last line waits with pthread_join for each of the 6 threads to finish before going on.

If the loop filled one shared description instead of args[t], thread 0 could read it after the loop had already written a later t into it. Which owner's values of i would then have no owner? And if the pthread_join loop were removed, when would main know the picture is finished?

CHECK

Thread 0 may read t = 1 or any later t, so two threads share those values of i, and owner 0's values, i = 0, 6, 12 and so on, are written by nobody. Without the joins main never knows, and it could check and time a picture still being written.

On the GPU, blockIdx.x keeps 14 blocks from repeating each other's work

A launch <<<B, T>>> makes, as the CUDA programming guide defines it, B blocks of T threads; threadIdx.x goes from 0 to T - 1 inside every block and blockIdx.x numbers the blocks; each block executes on one SM, one of the identical blocks of hardware the GPU is built from, 48 on the course GPU and 14 on the laptop, each with 4 schedulers; an SM handles a block's threads in consecutive sets of 32 that NVIDIA calls warps. The handout asks for one warp per scheduler, 192 on the course GPU as 48 blocks of 4 warps, and on the laptop's 56 schedulers that is 14 blocks of 4 warps.

With <<<14, 128>>>, number every warp of the launch as w = 4 x blockIdx.x + threadIdx.x / 32, dividing in whole numbers, and write its range. If warp w takes the values of i in turns, i = w, w + 56, w + 112 and so on, with its 32 threads splitting j as in Lab 1, which warp owns i = 1000? What goes wrong if w is computed from threadIdx.x alone?

CHECK

w goes from 0 to 55, and 1000 = 17 x 56 + 48, so warp 48 owns it. Computed from threadIdx.x alone, every block repeats warps 0 to 3, so their values of i get 14 owners each and every other value of i gets none.

The handout's fourth question tries other launches with the same number of warps. On the laptop <<<28, 64>>> and <<<7, 256>>> also make 56 warps; work out how many SMs can be working at once for each of the three launches, and whether any of them guarantees one warp per scheduler.

CHECK

<<<14, 128>>> and <<<28, 64>>> can keep 14 SMs working, <<<7, 256>>> at most 7, since each block executes on one SM. None guarantees one warp per scheduler, because the hardware chooses where blocks and warps go; with 7 blocks of 8 warps, at best 2 warps per scheduler on 7 SMs and nothing on the other 7.

Writing both versions, and what their times can show

The CPU version, mandelbrot_cpu_vector_multicore, starts one pthread per core, each executing your vector code on the values of i it owns in turns, then joins them all. The GPU version, mandelbrot_gpu_vector_multicore, computes w as above and loops over its own values of i, its 32 threads splitting j, and its launch function starts <<<number of SMs, 128>>>.

Compile and execute both files as in the Lab 2 setup, with -pthread for the CPU file, and write the two differences.

CHECK

Both must be exactly 0. A value near 0.0000448, or a multiple of it, suggests whole lines of the picture without an owner, from a shared description or a w that ignores blockIdx.x.

Write your CPU vector and multicore times and their ratio, and your GPU baseline and multicore times and their ratio. The counts above predict at most 5.98 for 6 owners in turns and 4.72 in bands.

CHECK

The laptop's times for this part were not recorded, so yours are the first. The CPU ratio should come out below 5.98, because thread start-up and a clock that falls when every core is busy also count. On the GPU, 56 warps instead of 1 can approach 56 times only if every warp gets equal work and a scheduler of its own.

A split needs one owner per place and similar work per owner

Gathered together, bands of equal size give 4.72 and turns give 5.98 on the same 6 threads; one shared description of the work leaves owner 0's lines unwritten; without blockIdx.x every block repeats the same 4 warps; and 56 warps can sit on only 7 of the 14 SMs.

Write one sentence on what a split has to get right, and why equal sizes and equal warp counts are not it.

CHECK

A split has to give every place exactly one owner and every owner nearly the same work: equal numbers of places carry very different work in this picture, 4.72 against 5.98, and equal numbers of warps can leave half the SMs empty.

The reading "6 threads, so 6 times" fails on the bands, which give 4.72 on the same hardware.

The handout's second question asks for the speedup over the single-core vector version with 8 cores, 6 on the laptop, and how the split affects it; the bands, the turns and your measured ratio answer it. Its third asks for the speedup over the single-warp GPU version with one warp per scheduler, its time against the CPU multicore version, and how the work was split; the warp numbering and your GPU ratio answer it. Its fourth asks whether <<<96, 64>>> and <<<24, 256>>> still give one warp per scheduler on the course GPU, <<<28, 64>>> and <<<7, 256>>> on the laptop, and how their times compare; the count of busy SMs above answers the first part, and your own times the second.

Lines of the picture left at 0 mean values of i with no owner, from a shared description or a missing blockIdx.x; a result that differs between executions means threads reading a shared description at different moments; a correct version far from 6 times means bands of unequal work, which turns fix; a GPU version no faster with more blocks means blocks crowded onto a few SMs, or warps onto a few schedulers.

Without code, splitting work between processors has two requirements, every piece done exactly once and every processor given a similar amount of work. Here, equal-sized bands fail the second, because the expensive part of the picture sits in the middle, and dealing the lines out in turns fixes it. Equal headcount per task and equal work per task are different things, so the question to ask is how the work was divided, not only into how many parts.

The guess at the top has its answer: about 5, 4.72, because the largest band carries 21.2 percent of the work instead of the 16.7 percent a sixth would be.

A harder question to finish with. A 6-thread version in turns predicts 5.98 but measures well below it. Name two causes that the repetition counts cannot see, and a measurement for each.

CHECK

Thread start-up and joining, measured by timing a version whose threads do no work; and a CPU clock that falls when every core is busy, measured by reading the clock with grep MHz /proc/cpuinfo while the version executes and comparing one busy core with six. Memory is an unlikely cause here, since the picture is 1024 x 1024 x 4 bytes = 4 MB, written once.

The lab pages who writes which place, and who finishes last and fixed by the chip, or made by the launch work these numbers out at length, and the notes on a single writer per place and the block of hardware a GPU chip is built from hold the short versions.
