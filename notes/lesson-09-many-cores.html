Lesson 9. Many CPU cores, many SMs

This lesson covers part 2 of Lab 2, where you write mandelbrot_cpu_vector_multicore, mandelbrot_gpu_vector_multicore and its launch, beginning from your ported Lab 2 vector versions. You need g++ with the POSIX threads library, the CUDA toolkit, and the Lab 2 starter folder, fetched with git clone https://github.com/accelerated-computing-class/lab2.git. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

Part 2 of Lab 2 spreads the vector version over many cores: on the CPU one thread of work per core, and on the GPU one set of 32 threads for each of the circuits that choose which instruction begins next. Either of two things can go wrong, and neither shows in the time alone. A split can give some places two writers and others none, and a correct split can still give one worker far more of the work, so that the job ends only when that worker does. How should a picture be split when its places need different amounts of work, and how do you know every part of the GPU got its share?

The first surprise at this step was that the part asks for threads at all:

"One question. So in this assignment I have to make threads? I thought I am just extending SIMD." / "Help me recall my working memory is zero."

Write a guess. Split the Lab 2 picture between 6 CPU threads, each taking a solid band of it, the first thread the top sixth, the next thread the sixth below that, and so on. If time follows the work, is the speedup, the time of one thread divided by the time of 6, about 6, about 5, or about 3?

Reading the Lab 2 reference and adding up its repetitions

constexpr float window_zoom = 1.0 / 10000.0f;
constexpr float window_x = -0.743643887 - 0.5 * window_zoom;
constexpr float window_y = 0.131825904 - 0.5 * window_zoom;
constexpr uint32_t default_max_iters = 2000;

void mandelbrot_cpu_scalar(uint32_t img_size, uint32_t max_iters, uint32_t *out) {
    for (uint64_t i = 0; i < img_size; ++i) {
        for (uint64_t j = 0; j < img_size; ++j) {
            float cx = (float(j) / float(img_size)) * window_zoom + window_x;
            float cy = (float(i) / float(img_size)) * window_zoom + window_y;

            float x2 = 0.0f;
            float y2 = 0.0f;
            float w = 0.0f;
            uint32_t iters = 0;
            while (x2 + y2 <= 4.0f && iters < max_iters) {
                float x = x2 - y2 + cx;
                float y = w - (x2 + y2) + cy;
                x2 = x * x;
                y2 = y * y;
                float z = x + y;
                w = z * z;
                ++iters;
            }

            out[i * img_size + j] = iters;
        }
    }
}

window_zoom is 1 divided by 10000, window_x is -0.743643887 minus half of window_zoom, and window_y is 0.131825904 minus half of window_zoom, each stored as a float, and default_max_iters is 2000. mandelbrot_cpu_scalar takes img_size and max_iters, two 32-bit whole numbers, and out, the address in memory where the answers go, one 32-bit whole number after another. For every pair (i, j) with i and j from 0 to img_size - 1, one place of the picture, cx is j divided by img_size, times window_zoom, plus window_x, and cy is i divided by img_size, times window_zoom, plus window_y. Then x2, y2 and w start out as 0 and iters as 0, and the while loop repeats its trip while x2 + y2 is at most 4 and iters is below max_iters: x becomes x2 minus y2 plus cx; y becomes w minus the sum x2 + y2, plus cy; x2 becomes x times x and y2 becomes y times y; z becomes x plus y; w becomes z times z; and iters goes up by 1. Once the while loop is left, iters is stored in out at entry i times img_size plus j.

The starter's main gives img_size the value 1024 and max_iters the value default_max_iters, so the Lab 2 picture has 1024 * 1024 = 1,048,576 places, and the places of one value of i fill 1024 neighbouring entries of out. Call one trip through the braces of the while loop a repetition; the iters stored for a place, its count, is the number of repetitions it made. Computed in 32-bit floats from the Lab 2 reference, the counts go from 69 to 2000 and add up to 138,219,822 repetitions.

Call the worker that writes a given place of out its owner; a split of the picture between workers is correct only if every place has exactly one owner. Assume that a repetition takes the same time on every worker. A single worker then takes time in proportion to all 138,219,822 repetitions, workers that work at once finish when the one with the most repetitions does, and the speedup of a split is 138,219,822 divided by the most repetitions any one worker has.

Cutting the 1024 values of i into bands and into turns

A CPU thread is a sequence of instructions that the operating system gives a core to execute. AMD's specifications give the handout's CPU, a Ryzen 7 7700, 8 cores with 2 hardware threads each, a hardware thread being one of the 2 threads a core can hold at once, and part 2 of the Fall 2025 handout asks for 8 CPU threads; the laptop's Ryzen 5 4600H has 6 cores with 2 hardware threads each, so this lesson splits between 6.

Write [a, b) for the values from a up to b - 1. Cut the 1024 values of i into 6 consecutive bands: divide 1024 by 6, round up, and write the bands from [0, 171) to the last one, checking that none is missing or repeated. Computed from the counts, the bands carry 20,219,285, 20,203,424, 28,346,172, 29,263,472, 19,303,420 and 20,884,049 repetitions; work out each band's percent of the work and the speedup.

CHECK 
1024 / 6 = 170.67, rounded up 171;  6 * 171 = 1026, 2 too many for the last band
[0,171) [171,342) [342,513) [513,684) [684,855) [855,1024)
sizes 171, 171, 171, 171, 171 and 169 = 1024, each band beginning where the one before ends
percent: 14.6, 14.6, 20.5, 21.2, 14.0, 15.1
speedup: 138,219,822 / 29,263,472 = 4.72, not 6

Deal the values out in turns instead: owner t takes i = t, t + 6, t + 12 and so on while i is below 1024. Which owner gets i = 1023, and why can no value of i have two owners? Computed from the counts, the owners carry 23,029,821, 23,043,321, 23,099,034, 23,079,169, 22,974,325 and 22,994,152 repetitions; work out the speedup.

CHECK

1023 = 170 * 6 + 3, so owner 3 gets it; each value of i leaves exactly one remainder when divided by 6, so it has exactly one owner. The speedup is 138,219,822 / 23,099,034 = 5.98.

For the handout's 8 threads, each band holds 1024 / 8 = 128 values of i exactly. Computed from the counts, the band with the most work carries 22,059,919 repetitions, and in turns the owner with the most carries 17,303,293. Work out both speedups.

CHECK

Bands give 138,219,822 / 22,059,919 = 6.27 and turns 138,219,822 / 17,303,293 = 7.99, of 8.

Creating the CPU threads and waiting for each to finish

The POSIX threads library starts a thread with pthread_create, which takes the address of a handle for the thread, nullptr for the default settings, the function the thread executes and one address handed to that function; it returns as soon as the thread exists, so the new thread may read what that address points to at any later moment. pthread_join waits until the thread of a handle has finished. A start written for 6 owners in turns reads:

struct Args { uint32_t first; uint32_t step; uint32_t *out; };
Args args[6];
pthread_t tid[6];
for (uint32_t t = 0; t < 6; ++t) {
    args[t] = {t, 6, out};
    pthread_create(&tid[t], nullptr, worker, &args[t]);
}
for (uint32_t t = 0; t < 6; ++t) pthread_join(tid[t], nullptr);

Args describes what one worker needs: first, the first i it owns, step, the distance to its next i, and out, the address of the picture. args holds 6 such descriptions and tid 6 thread handles, all kept until the function that holds them ends. For t from 0 to 5, worker t's own description, args[t], is filled with first t, step 6 and the picture's address, and pthread_create starts a thread executing the function worker on the address of args[t]. After that loop, pthread_join waits for each of the 6 threads in turn to finish.

worker is the function written at this step for each thread: it takes the address of its description, and for i from first, in steps of step, while i is below 1024, it computes the 1024 places of that i with the vector code and stores their counts in out.

Suppose the loop filled one shared description instead of args[t]. Thread 0 may read it after the loop has already written t = 1 or a later t into it: which values of i would then have two owners, and which none? And if the pthread_join loop were removed, how would the function know the picture is finished?

CHECK

Thread 0 then takes the values of the t it read, which another thread takes too, and nobody takes owner 0's values, i = 0, 6, 12 and so on. Without the joins nothing tells the function that the threads have finished, and it could return, to be checked and timed, while they are still writing.

Before each version the starter sets every entry of out to 0, and after it the starter prints what this function returns:

double difference(
    uint32_t img_size,
    uint32_t max_iters,
    std::vector<uint32_t> &result,
    std::vector<uint32_t> &ref_result) {
    int64_t diff = 0;
    for (uint32_t i = 0; i < img_size; i++) {
        for (uint32_t j = 0; j < img_size; j++) {
            diff +=
                abs(int(result[i * img_size + j]) - int(ref_result[i * img_size + j]));
        }
    }
    return diff / double(img_size * img_size * max_iters);
}

difference sets a 64-bit whole number diff to 0, visits every place (i, j), adds the size of the gap between the version's count in result and the reference's count in ref_result, and returns diff divided by img_size times img_size times max_iters; main prints it as the average output difference from the reference.

Owner 0's values of i, 1024 / 6 rounded up = 171 of them, carry 23,029,821 repetitions, computed from the counts. If they are never written, what does difference print?

CHECK 
divisor:  1024 * 1024 * 2000 = 2,097,152,000
owner 0's values left at 0:  23,029,821 / 2,097,152,000 = 0.0110

Numbering warps across blocks with blockIdx.x

On the GPU, a function that executes there is a kernel, and each execution of it from its beginning is a thread. A kernel is started from the CPU with kernel<<<B, T>>>(arguments), which, as NVIDIA's CUDA programming guide defines it, starts B blocks of T threads each; inside the kernel, threadIdx.x is a thread's number in its block, from 0 to T - 1, blockIdx.x is its block's number, from 0 to B - 1, and blockDim.x is T. The GPU chip is built from identical blocks of hardware, which NVIDIA calls SMs, and the guide puts every block on one SM; the course GPU, an RTX 4000 Ada, has 48 SMs by NVIDIA's specification, and the laptop's GTX 1650 reports 14 through cudaGetDeviceProperties, in multiProcessorCount. Each SM of both GPUs has 4 schedulers, the circuits that choose which instruction begins next, and handles a block's threads in consecutive sets of 32 that begin each instruction together, which NVIDIA calls warps, each warp on one scheduler.

Part 2 of the handout asks the GPU version for one warp per scheduler: 48 * 4 = 192 warps on the course GPU, as 48 blocks of 4 warps, <<<48, 128>>>, and 14 * 4 = 56 on the laptop, <<<14, 128>>>. The Lab 2 GPU vector version, started with <<<1, 32>>> as a single warp, has thread t take j = t, t + 32, t + 64 and so on for every i; call it the single-warp version.

With <<<14, 128>>>, number every warp of the launch as w = 4 * blockIdx.x + threadIdx.x / 32, dividing in whole numbers, and write its range. Let warp w take the values of i in turns, i = w, w + 56, w + 112 and so on, its thread with number threadIdx.x % 32 in the warp taking j as thread t did in the single-warp version. Which warp owns i = 1000? If w were computed from threadIdx.x alone, which values of i would be computed, by how many warps each? Computed from the counts, those values, 76 of them, carry 10,410,388 repetitions; what would difference print?

CHECK 
w = 4 * blockIdx.x + threadIdx.x / 32 goes from 4 * 0 + 0 = 0 to 4 * 13 + 3 = 55
1000 = 17 * 56 + 48 -> warp 48 owns i = 1000
w from threadIdx.x alone: 0 to 3 in every block, so only i = 0 to 3, 56 to 59 and so on
  are computed, each by 14 warps, one per block, and every other value of i by none
difference: (138,219,822 - 10,410,388) / 2,097,152,000 = 127,809,434 / 2,097,152,000 = 0.0609

The handout's fourth question tries other launches with the same number of warps. On the laptop, <<<28, 64>>> and <<<7, 256>>> also make 56 warps, and on the course GPU <<<96, 64>>> and <<<24, 256>>> make 192. For each launch, how many SMs can be working at once, and does any launch guarantee one warp per scheduler?

CHECK 
laptop:      <<<14, 128>>> 14 * 4 = 56 warps, at most 14 SMs
             <<<28, 64>>>  28 * 2 = 56 warps, at most 14 SMs
             <<<7, 256>>>   7 * 8 = 56 warps, at most 7 SMs
course GPU:  <<<96, 64>>>  96 * 2 = 192 warps, at most 48 SMs
             <<<24, 256>>> 24 * 8 = 192 warps, at most 24 SMs

Every block sits on one SM, so 7 blocks keep at most 7 SMs working and 24 blocks at most 24; with 7 blocks of 8 warps, each working SM holds 8 warps on its 4 schedulers, 2 per scheduler if they are spread evenly, while the other 7 SMs hold nothing. None of the launches guarantees one warp per scheduler, because the hardware chooses which SM takes each block.

Since the 32 threads of a warp begin each instruction together, NVIDIA's CUDA programming guide has a warp keep executing a loop, with its finished threads switched off, until its last thread leaves it, so a warp repeats until the slowest of its places is done. Call one repetition of the loop by a whole warp a warp-repetition. Computed in 32-bit floats from the Lab 2 reference, the single-warp version needs 8,792,320 warp-repetitions, and with 56 warps in turns over i, the warp with the most needs 168,029.

How many values of i do warps 0 to 15 take, and warps 16 to 55? If every value of i carried the same work, what speedup would 56 warps give over one, and what do the warp-repetitions give, if each warp has a scheduler of its own and time follows warp-repetitions?

CHECK 
1024 = 18 * 56 + 16 -> warps 0 to 15 take 19 values of i, warps 16 to 55 take 18
equal work per value of i:  1024 / 19 = 53.9
from the warp-repetitions:  8,792,320 / 168,029 = 52.3, of 56

Writing both versions and timing them

The CPU version, mandelbrot_cpu_vector_multicore, starts one thread per core with pthread_create, each executing your vector code on the values of i it owns in turns, and then joins them all with pthread_join. The GPU version, mandelbrot_gpu_vector_multicore, computes w = 4 * blockIdx.x + threadIdx.x / 32 and loops over its own values of i in steps of the launch's number of warps, i = w, w + 56 and so on on the laptop, its 32 threads splitting j, and launch_mandelbrot_gpu_vector_multicore starts it with <<<number of SMs, 128>>>. Compile and execute both files from the lab2 folder:

g++ -O3 -march=native -std=c++17 -pthread mandelbrot_cpu_2.cpp -o mandelbrot_cpu_2
nvcc -O3 -arch=sm_75 -std=c++17 mandelbrot_gpu_2.cu -o mandelbrot_gpu_2
./mandelbrot_cpu_2 && ./mandelbrot_gpu_2

g++ compiles the CPU file with full optimization for every instruction this CPU has, as 2017 C++, and -pthread adds the POSIX threads library; nvcc compiles the GPU file for compute capability 7.5, the GTX 1650's, so put your own GPU's number after sm_; and the last command executes the CPU program and, if it succeeds, the GPU program, each printing a time and a difference for every version.

Write the difference printed for each multicore version, and what 0.0110 or 0.0609 would point to.

CHECK

Both must print exactly 0. A printed 0.0110 matches owner 0's 171 values of i left at 0, from a shared description, and 0.0609 matches warps numbered from threadIdx.x alone, which leave 948 of the 1024 values of i at 0.

The counts leave out two costs on the CPU. pthread_create and pthread_join take time of their own. And AMD's specification gives the Ryzen 5 4600H a base clock of 3.0 GHz and a boost clock of up to 4.0 GHz, which its footnote defines as the most a single core reaches on a single-threaded workload, so 6 busy cores may each be slower than the 1 they are compared with.

Write your CPU vector and multicore times and their ratio, and your GPU single-warp and multicore times and their ratio. Set them beside 5.98 for 6 owners in turns and 52.3 for 56 warps.

CHECK

The laptop's times for this part were not recorded in the chats, so yours are the first. A CPU ratio below 5.98 can come from the thread start and join and from a clock below its single-core boost with 6 cores busy; a GPU ratio below 52.3 from warps that share a scheduler or SMs left empty by the hardware's choice of where blocks go.

Gathering what a split has to get right

Bands of 171 or 169 values of i give 4.72 on 6 threads and turns give 5.98, or 6.27 and 7.99 on 8; a shared description leaves owner 0's 171 values of i unwritten and prints 0.0110; warps numbered without blockIdx.x leave 948 values of i unwritten and print 0.0609; <<<7, 256>>> makes the same 56 warps as <<<14, 128>>> but can keep only 7 of the 14 SMs working; and 56 warps in turns can give at most 52.3.

Write one sentence on what a split has to get right, and why equal sizes and equal warp counts are not it.

CHECK

A split has to give every place exactly one owner and every owner nearly the same work: equal numbers of places carry very different work in this picture, 4.72 against 5.98 on the same 6 threads, and equal numbers of warps can leave half the SMs empty, 7 of 14.

The reading "6 threads, so 6 times" fails on the bands, which give 4.72 on the same 6 threads, because the band from 513 to 683 carries 21.2 percent of the work instead of a sixth.

The handout's second question asks for the speedup over the single-core vector version with 8 cores, 6 on the laptop, and how the split affects it; the bands, the turns and your measured ratio answer it. Its third asks for the speedup over the single-warp GPU version with one warp per scheduler, its time against the CPU multicore version, and how the work was split; the warp numbering, the 52.3 and your GPU ratio answer it. Its fourth asks whether <<<96, 64>>> and <<<24, 256>>> still give one warp per scheduler on the course GPU and how their times compare, on the laptop <<<28, 64>>> and <<<7, 256>>>; the 48 and 24 SMs that the course GPU's launches can keep working, the 14 and 7 of the laptop's, and the hardware's own choice of where blocks go answer the first part, and your own times the second.

Values of i left at 0 mean values with no owner, from a shared description or a w without blockIdx.x, and the printed 0.0110 and 0.0609 match those two. A result that differs between executions means threads reading a shared description at different moments. A correct version far from 6 times means bands of unequal work, which turns fix. A GPU version no faster with more blocks means blocks crowded onto a few SMs, or warps onto a few schedulers.

Splitting work between processors has two requirements, every piece done exactly once and every processor given a similar amount of work. Here equal-sized bands fail the second, because the expensive part of the picture sits in the middle bands, and dealing the values of i out in turns fixes it. Equal headcount per task and equal work per task are different things, so the question to ask of any split is how the work was divided, not only into how many parts.

The speedup asked for at the start is about 5: the counts give 4.72, because the largest band carries 21.2 percent of the work instead of the 100 / 6 = 16.7 percent of a sixth.

On the course GPU, <<<48, 128>>> makes 192 warps, w = 4 * blockIdx.x + threadIdx.x / 32, taking the values of i in turns, i = w, w + 192 and so on. Which warp owns i = 1000, and how many values of i does each warp take? Even if every value of i carried the same work, what speedup over one warp could the 192 warps give?

CHECK

1000 = 5 * 192 + 40, so warp 40 owns it. 1024 = 5 * 192 + 64, so warps 0 to 63 take 6 values of i and warps 64 to 191 take 5. With equal work per value of i the job ends with a warp of 6, at most 1024 / 6 = 170.7 times one warp, not 192: 64 warps carry a sixth value while 128 wait for them.

The lab pages who writes which place, and who finishes last and fixed by the chip, or made by the launch work these numbers out at length, and the notes on a single writer per place and the block of hardware a GPU chip is built from hold the short versions.
