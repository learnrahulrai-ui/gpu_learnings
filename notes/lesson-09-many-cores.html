The story

Part 2 of Lab 2 spreads the vector version over many cores: one CPU thread per core, and on the GPU one set of 32 threads for each of its schedulers.

Either of two things can go wrong, and neither shows in the time alone. A split can give some places two workers and others none. And a correct split can still give one worker far more of the work, so that the job ends only when that worker does.

How do you split a picture whose work is unevenly spread, and how do you know every SM got its share?

L05 Code that starts 6 CPU threads in turns, copied from page 14: from: POSIX threads

struct Args { uint32_t first; uint32_t step; uint32_t *out; };
Args args[6];
pthread_t tid[6];
for (uint32_t t = 0; t < 6; ++t) {
    args[t] = {t, 6, out};
    pthread_create(&tid[t], nullptr, worker, &args[t]);
}
for (uint32_t t = 0; t < 6; ++t) pthread_join(tid[t], nullptr);

Tempting answer that fails: "6 threads, so 6 times". L03 refutes it on the same hardware.

When it goes wrong

  • Some lines of the picture are 0 and the rest correct. Those values of i have no owner: a shared Args variable, or blockIdx.x left out (L06, L08).
  • The result differs from one execution to the next. Threads read a shared Args variable at different moments (L06).
  • Correct, but far from 6 times on 6 threads. Bands carry unequal work (L03); split in turns (L04).
  • The GPU version is no faster with more blocks. Blocks crowd onto a few SMs, or warps onto a few schedulers (L09).

In plain words

Splitting work between processors has two requirements: every piece done exactly once, and every processor given a similar amount of work. Here, splitting the picture into equal-sized bands fails the second, because the expensive part sits in the middle; dealing the lines out in turns fixes it.

For a manager: equal headcount per task and equal work per task are different things. Ask how the work was divided, not only into how many parts.
