The story

The second prelab file, warp_scheduler.cu, launches more and more threads, each doing one long chain of multiply-adds, and prints operations per second for each launch. The lab asks when the GPU reaches its largest rate, and what the multiply-add's wait says about it.

The file was written for the course GPU, with that GPU's SM count typed in as the number 48. On a laptop with 14 SMs it still compiles and executes, and prints a table that looks just as clean.

How many threads does a GPU need to stay busy, and how does that differ from how many it can hold?

Guess first

The GTX 1650 has 14 SMs with 4 schedulers each. Guess how many sets of 32 threads it needs to keep every FP32 unit busy with chains of multiply-adds: 56, 112 or 448?

Write your guess on paper now, before any calculation on this page.

Work it out

L01 Course machine for Lab 2 (Fall 2025 handout): an NVIDIA RTX 4000 Ada at 2.175 GHz with 48 SMs; each SM has 4 warp schedulers (192 in all), and each scheduler holds up to 12 warps, a warp being NVIDIA's name for a set of 32 consecutive threads of a block. Each SM has 128 FP32 units. from: Lab 2 handout (Fall 2025), NVIDIA Ada specification

L02 The laptop's GTX 1650 (Turing): 14 SMs with 4 schedulers each (56 in all) and 64 FP32 units per SM; an SM holds at most 32 warps and 16 blocks. from: your hardware table, NVIDIA Turing Tuning Guide

L03 The lines of warp_scheduler.cu that build the launch and the printed numbers, copied from page 12: from: Lab 2 starter code

uint32_t block_size = default_tile_size * num_threads_per_block;
dim3 grid(N / block_size);
tail_latency_fma<default_num_ops, default_tile_size><<<grid, block>>>(in, out, N);
int N = block_size * 48 * multiplier;
double flops = ((double)N * default_num_ops * 2) / time_in_seconds;
uint32_t warps = (N / block_size) * (num_threads_per_block / 32);

Read the code in English, line by line

  1. uint32_t block_size = default_tile_size * num_threads_per_block;Numbers handled per block: the default tile size (32) times the threads per block (64 by default), 2048.
  2. dim3 grid(N / block_size);Blocks to launch: N divided by 2048, in whole-number division.
  3. tail_latency_fma<default_num_ops, default_tile_size><<<grid, block>>>(in, out, N);Launch the kernel with the default tile size and number of updates fixed in; the tile size handed to this launcher is never used.
  4. int N = block_size * 48 * multiplier;Total numbers for one setting of the sweep: 2048 times 48 times the multiplier. The 48 is typed in.
  5. double flops = ((double)N * default_num_ops * 2) / time_in_seconds;Operations per second: every number gets 5260 multiply-adds, each counted as 2 operations, divided by the measured time.
  6. uint32_t warps = (N / block_size) * (num_threads_per_block / 32);The printed warps: blocks times warps per block.

L04 From the starter: 64 threads per block, each handling 32 numbers, so 2,048 numbers per block; each number goes through tmp += tmp * 3.0f 263 x 20 = 5,260 times, each step needing the one before; N = 2,048 x 48 x m numbers for m = 1 to 48; it prints warps = blocks x 2 and operations per second = N x 5,260 x 2 / time. from: Lab 2 starter code, L03

Connect the numbers

L14 DO Collect L06 (768 and 112 needed), L07 (2,304 and 448 held), L08 (99 percent at 768), L09 (12.5 percent more work, 87 percent more time), L10 (the 48 on 14 SMs). Answer the prelab's fourth question in one sentence: when does the sweep reach its largest rate, and what does the FFMA's wait say about it? from: L06, L07, L08, L09, L10

CHECK 
The rate peaks once each scheduler has enough independent warps to begin an FFMA at every chance
during the 4-cycle wait: 4 per scheduler (768 warps) on the course GPU, 2 per scheduler (112) on
the laptop; past that, extra warps add nothing and can add a round of waiting.

Tempting answer that fails: "fill every SM to its maximum of warps". L07 and L09 refute it: the
target is a third of the ceiling, and going past it cost 87 percent more time.

When it goes wrong

  • The laptop's table has no clean peak. The 48 spreads blocks unevenly over 14 SMs (L10); use the SM count the GPU reports (L13).
  • The laptop peaks at a different warp count than the course GPU. Correct: it needs 2 warps per scheduler, not 4 (L06).
  • A small step up in warps costs far more time. A second round of blocks (L09).

In plain words

A GPU hides waiting by switching between many independent sets of threads. It needs only enough of them to cover each wait, here a third or a quarter of what it can hold. Past that point more threads add nothing, and a launch slightly too large can add a whole extra round of time.

For a manager: "the hardware supports N" is a ceiling, not a target. The right number comes from how long each step of the work waits, and it differs between machines.
