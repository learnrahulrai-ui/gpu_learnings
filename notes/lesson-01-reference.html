The story

Lab 1 begins with a function that is already written, mandelbrot_cpu_scalar: the reference every later version is checked against. Most people skim it, because it is short and it works. Every later speedup in the course, however, depends on two facts hidden in it: where the numbers it works on come from, and how unequal the work per place is.

The learner did not skim it. They refused the claim that squaring from zero does anything, asked what the loop is leaving, and asked why the code subtracts when the formula adds.

How much work does one place cost, and can anyone tell before its loop is done?

Guess first

The 256 by 256 picture has 65,536 places, and each place repeats the loop between 1 and 1000 times. Guess the share of all repetitions done by the places that reach 1000: about a quarter, about half, or almost all?

Write your guess on paper now, before any calculation on this page.

Your words: "if i start at 00 squaring means nothing there shall be no change at all ever" / "whyy would i start form 00 when i alreadyyy started with 1 0" / "You have not defined escape from what ... A point 9 7 is going to be at 9 7."

Work it out

L01 The body of the reference for one place (i, j), copied from the Lab 1 starter; around it, i and j each go from 0 to img_size - 1: from: Lab 1 starter code

float cx = (float(j) / float(img_size)) * 2.5f - 2.0f;
float cy = (float(i) / float(img_size)) * 2.5f - 1.25f;
float x2 = 0.0f;
float y2 = 0.0f;
float w = 0.0f;
uint32_t iters = 0;
while (x2 + y2 <= 4.0f && iters < max_iters) {
    float x = x2 - y2 + cx;        // line A
    float y = w - x2 - y2 + cy;    // line B
    x2 = x * x;                    // line C
    y2 = y * y;                    // line D
    float z = x + y;               // line E
    w = z * z;                     // line F
    ++iters;
}
out[i * img_size + j] = iters;

Read the code in English, line by line

  1. float cx = (float(j) / float(img_size)) * 2.5f - 2.0f;Turn j and img_size into fractions, divide j by img_size, multiply by 2.5, subtract 2.0, and keep the result in a fraction named cx. The f after a number marks it as a 32-bit fraction (a float).
  2. float cy = (float(i) / float(img_size)) * 2.5f - 1.25f;Do the same with i, but subtract 1.25, and keep the result in cy.
  3. float x2 = 0.0f;Make a fraction named x2 holding 0.
  4. float y2 = 0.0f;Make a fraction named y2 holding 0.
  5. float w = 0.0f;Make a fraction named w holding 0.
  6. uint32_t iters = 0;Make a 32-bit whole number named iters holding 0. It will count repetitions.
  7. while (x2 + y2 <= 4.0f && iters < max_iters) {Before each repetition, test two things: is x2 plus y2 at most 4, and is iters below max_iters? If both are true, do the lines inside the braces once and test again. If either is false, continue after the closing brace.
  8. float x = x2 - y2 + cx; // line ALine A: subtract y2 from x2, add cx, keep it in x.
  9. float y = w - x2 - y2 + cy; // line BLine B: from w subtract x2, then subtract y2, then add cy, keep it in y.
  10. x2 = x * x; // line CLine C: multiply x by itself and put the result in x2, replacing the old x2.
  11. y2 = y * y; // line DLine D: multiply y by itself and put the result in y2.
  12. float z = x + y; // line ELine E: add x and y, keep it in z.
  13. w = z * z; // line FLine F: multiply z by itself and put the result in w.
  14. ++iters;Add 1 to iters.
  15. }End of the block opened by the matching brace above.
  16. out[i * img_size + j] = iters;Store the whole number iters into the array out, at place number i times img_size plus j.

L02 From L01: i counts down the picture and j counts right; the result for (i, j) goes to out[i * img_size + j]. The learner called that sheet of results the image paper. cx is computed from j alone and cy from i alone; the pair (cx, cy) is a point on a second sheet with (0, 0) at its center, the graph paper. The learner named (cx, cy) the middleman pair. from: L01

L03 DO img_size = 256. Place (64, 64): cx = 64 / 256 x 2.5 - 2.0 = ____ , cy = 64 / 256 x 2.5 - 1.25 = ____ . Smallest cx (j = 0) = ____ ; largest (j = 255) = ____ ; the value cx never reaches = ____ . from: L01, L02

CHECK 
64 / 256 = 0.25, x 2.5 = 0.625: cx = -1.375, cy = -0.625
j = 0: -2.0; j = 255: 255/256 x 2.5 - 2.0 = 0.490234375; never 0.5
The graph paper covered: x from -2.0 up to 0.5, y from -1.25 up to 1.25.
img_size only sets how finely that same part is sampled.

L04 From L01, a repetition is lines A to F and ++iters, once, in that order. Before each, the loop checks x2 + y2 <= 4 and iters < max_iters; it leaves the while loop when either is false, and iters is stored. x2, y2 and w begin at 0. from: L01

Check before repetition 2: x2 + y2 = ____ . Repetition 2: x = ____ , y = ____ , x2 = ____ , y2 = ____ , z = ____ , w = ____ . Check before repetition 3 = ____ . from: L01, L03, L04

CHECK

L06 DO Repetition 3: x = ____ , y = ____ , x2 = ____ , y2 = ____ . Check before repetition 4 = ____ , so the loop ____ and stores iters = ____ . Did x2 + y2 go down at any check? ____ . from: L04, L05

CHECK

L07 A repetition is meant to turn the point (x, y) into (x times x - y times y + cx, 2 times x times y + cy). The code never multiplies x by y: line E makes z = x + y and line F makes w = z times z. from: Mandelbrot iteration, L01

L08 DO Expand (x + y) times (x + y) = ____ . So 2 times x times y = w - ____ - ____ . Check with repetition 2 of L05 (x = 0.125, y = 1.09375): 2 times x times y = ____ ; w - x2 - y2 = 1.485352 - 0.015625 - 1.196289 = ____ . from: L05, L07

CHECK 
x times x + 2 times x times y + y times y = x2 + 2xy + y2
2xy = w - x2 - y2, so line B is 2xy + cy
2 x 0.125 x 1.09375 = 0.273438; 1.485352 - 0.015625 - 1.196289 = 0.273438
Trading the multiply x times y for z times z reuses x2 and y2, which the check needs anyway.

When it goes wrong

  • Your total differs from 16,274,722 by a little. Different rounding: compiler flags, or a line written in another order (L10).
  • Your total is 0 or tiny. The sum reads result instead of ref_result, or adds before the reference is computed (L09).
  • The picture at -r 512 shows the same shape as at 256. Correct: img_size only sets how finely the same part of the graph paper is sampled (L03).

In plain words

The picture is made of tens of thousands of small, independent calculations, and they are wildly unequal: a quarter of them do nearly all the work, and nobody can tell which ones in advance. That one fact shapes everything that follows, from how to split the work to why splitting it evenly by count fails.

For a manager: "we split the job into equal parts" means nothing until someone checks that the parts are equal in work, not just in number.

Your guess against the machine

Compare with the guess you wrote at the top. Count it as close if it is within a fifth of the real value, or on the right side of a yes-or-no. Add one mark to your paper tally if it was close.

The interviewer's next question

Splitting by bands of i gave 2.10 out of 4. Without knowing any iters in advance, how would you split the 256 values of i between 4 workers so that each gets about a quarter of the work, and what speedup would you expect?

CHECK 
Interleave: worker k takes i = k, k + 4, k + 8, ...; each worker gets a slice of every band,
cheap and costly alike. Computed on the real iters: shares 25.2, 25.0, 24.9, 25.0 percent,
speedup 3.97 out of 4. No knowledge of iters is needed, only that costly places sit together.
