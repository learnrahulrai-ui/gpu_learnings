Lesson 1. The reference program, by hand

This lesson covers the reference function of Lab 1, part 1, which is already written. What you add is a total of all counts, printed by main, and it needs only the Lab 1 folder compiled. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

Every later version in both labs is checked against mandelbrot_cpu_scalar, so its numbers come first. Hidden in its few lines are the facts that decide every speedup that follows: where the pair of fractions it works on comes from, and how unequal the work per place is. Most people skim it, because it is short and it works. How much work does one place cost, and can anyone tell before its loop is done?

Its first lines look like they do nothing, and that is where the questions at this step began:

"if i start at 00 squaring means nothing there shall be no change at all ever" / "whyy would i start form 00 when i alreadyyy started with 1 0" / "You have not defined escape from what ... A point 9 7 is going to be at 9 7."

Write a guess before any arithmetic. The 256 by 256 picture has 65,536 places, and each place repeats the loop between 1 and 1000 times. What share of all repetitions do the places that reach 1000 account for: about a quarter, about half, or almost all?

cx comes from j alone and cy from i alone, and img_size only sets how many samples cover -2.0 to 0.5

float cx = (float(j) / float(img_size)) * 2.5f - 2.0f;
float cy = (float(i) / float(img_size)) * 2.5f - 1.25f;
float x2 = 0.0f;
float y2 = 0.0f;
float w = 0.0f;
uint32_t iters = 0;
while (x2 + y2 <= 4.0f && iters < max_iters) {
    float x = x2 - y2 + cx;        // line A
    float y = w - x2 - y2 + cy;    // line B
    x2 = x * x;                    // line C
    y2 = y * y;                    // line D
    float z = x + y;               // line E
    w = z * z;                     // line F
    ++iters;
}
out[i * img_size + j] = iters;

Read in English, the first two lines turn j and i into the pair of fractions (cx, cy): j divided by img_size, times 2.5, minus 2.0 gives cx, and i treated the same way but minus 1.25 gives cy, where the f after each number marks a 32-bit fraction, a float. The next four lines set x2, y2 and w to 0 and the count, iters, to 0. The while line repeats what is inside as long as x2 + y2 is at most 4 and the count is below max_iters. Inside, line A makes x from x2 minus y2 plus cx, line B makes y from w minus x2 minus y2 plus cy, lines C and D square x and y into x2 and y2, line E adds x and y into z, line F squares z into w, and the count goes up by 1. The last line stores the count at place number i times img_size plus j of out.

Around those lines, i counts down the picture and j counts right, each from 0 to img_size - 1. On these pages the sheet of stored counts is called the image paper, and the second sheet, with (0, 0) at its center and (cx, cy) as a point on it, is the graph paper; (cx, cy) itself is the middleman pair, because the loop works on it and never on (i, j).

Take img_size = 256 and the place (64, 64). Work out cx = 64 / 256 x 2.5 - 2.0 and cy = 64 / 256 x 2.5 - 1.25. Then find the smallest cx, at j = 0, the largest, at j = 255, and the value that cx never reaches.

CHECK 
64 / 256 = 0.25,   0.25 x 2.5 = 0.625
cx = 0.625 - 2.0  = -1.375
cy = 0.625 - 1.25 = -0.625

j = 0   : cx = -2.0
j = 255 : 255 / 256 x 2.5 - 2.0 = 0.490234375
j / 256 never reaches 1, so cx never reaches 1 x 2.5 - 2.0 = 0.5

The part of the graph paper covered stretches from -2.0 up to 0.5 left to right and from -1.25 up to 1.25 top to bottom, whatever img_size is; img_size sets only how finely that same part is sampled.

Place (64, 64) leaves the loop after 3 repetitions, and its check goes down before it goes up

A repetition is lines A to F and the count, once, in that order. Before each one the loop checks x2 + y2 <= 4 and iters < max_iters, and it leaves the while loop as soon as either is false; the count at that moment is what gets stored. x2, y2 and w begin at 0.

Work repetitions 1 and 2 for place (64, 64), with cx = -1.375 and cy = -0.625. Repetition 1 gives x = 0 - 0 + cx and y = 0 - 0 - 0 + cy; from them work out x2, y2, z = x + y and w. Write the check x2 + y2 before repetition 2, then work repetition 2 the same way and write the check before repetition 3.

CHECK 
rep 1: x = -1.375   y = -0.625
       x2 = 1.890625   y2 = 0.390625   z = -2.0   w = 4.0
check before rep 2: 1.890625 + 0.390625 = 2.281250, at most 4

rep 2: x = 1.890625 - 0.390625 - 1.375         = 0.125
       y = 4.0 - 1.890625 - 0.390625 - 0.625   = 1.09375
       x2 = 0.015625   y2 = 1.196289   z = 1.21875   w = 1.485352
check before rep 3: 0.015625 + 1.196289 = 1.211914, at most 4

Work repetition 3 from those values, write the check before repetition 4, and say what the loop does and which count it stores. Did x2 + y2 go down at any check?

CHECK 
rep 3: x = 0.015625 - 1.196289 - 1.375             = -2.555664
       y = 1.485352 - 0.015625 - 1.196289 - 0.625  = -0.351562
       x2 = 6.531418   y2 = 0.123596
check before rep 4: 6.655015, above 4: leave the while loop, iters = 3

The checks read 2.281250, 1.211914 and 6.655015: down, then up. Only the check decides when the loop is left, and the size does not grow steadily, so the count cannot be read off (cx, cy) in advance.

Line B holds 2xy without ever multiplying x by y

A repetition is meant to turn the point (x, y) into (x times x - y times y + cx, 2 times x times y + cy), the step that defines the Mandelbrot set, yet no line of the reference multiplies x by y. Line E makes z = x + y and line F makes w = z times z instead.

Expand (x + y) times (x + y) on paper, and from it write 2 times x times y in terms of w, x2 and y2. Then check the result with repetition 2 of place (64, 64), where x = 0.125, y = 1.09375, x2 = 0.015625, y2 = 1.196289 and w = 1.485352.

CHECK 
(x + y) times (x + y) = x times x + 2 times x times y + y times y = x2 + 2xy + y2
so 2xy = w - x2 - y2, and line B is 2xy + cy

2 x 0.125 x 1.09375            = 0.273438
1.485352 - 0.015625 - 1.196289  = 0.273438

Trading the multiply of x by y for z times z reuses x2 and y2, which the check needs anyway.

A quarter of the places do 97.7 percent of the work

To see the cost of every place at once, add a check of your own to main: after the reference is computed, add up all of ref_result in a 64-bit integer and print the total with a word such as "CPU total" before it. The few lines needed are a for loop over ref_result and std::cout, and every later version can be checked against the same total.

Compile and execute as before and write your total. The laptop printed 16,274,722. If yours differs, write what could change a count.

CHECK

A different total means a different picture: a changed line, img_size or max_iters, or a compiler that rounds differently, for example by merging a multiply and an add into one fused instruction. Every later version is checked against this same total, so a mismatch here has to be settled first.

Computed with the reference's own lines for all 65,536 places at img_size 256 and max_iters 1000, 3,781 places stop after 1 repetition, 15,902 reach 1000, and all the counts add up to 16,274,722.

Work out the average count per place, the share of places that reach 1000, and the share of all repetitions those places account for, 15,902 x 1000 / 16,274,722.

CHECK 
average: 16,274,722 / 65,536 = 248.3
places at 1000: 15,902 / 65,536 = 24.3 percent
their repetitions: 15,902,000 / 16,274,722 = 97.7 percent

Split the same picture between 4 workers in bands of 64 values of i, 0 to 63, 64 to 127, 128 to 191 and 192 to 255, and the bands carry 462,567, 7,558,684, 7,747,009 and 506,462 repetitions.

If time follows repetitions, the job ends when the largest band ends. Work out the speedup of the 4 workers over 1, and compare it with the 4 that "4 workers, 4 times faster" expects.

CHECK

16,274,722 / 7,747,009 = 2.10, not 4: the costly places sit together in the middle bands, so two workers finish almost at once and then wait.

From the reference's printed time on the laptop, 61.6 ms for 16,274,722 repetitions, work out the time of one repetition, and your own from your time and total.

CHECK

61.6 ms / 16,274,722 = 3.79 ns per repetition on one core of the laptop. Every later version tries to divide this number.

Any split of this picture has to be judged by repetitions, not by places

Gathered together, this page has shown that img_size sets only how finely the same part of the graph paper is sampled; that the check at (64, 64) went down before it went up; that line B carries 2xy without multiplying x by y; that 24.3 percent of the places do 97.7 percent of the work; that 4 bands of equal size give 2.10 times, not 4; and that one repetition costs 3.79 ns on one core.

Write one sentence on what any faster version of this program has to respect about the work per place.

CHECK

The cost of a place ranges from 1 to 1000 repetitions, cannot be read off (cx, cy) before its loop is done, and the costly places sit together, so any split of the picture into workers, vectors or threads has to be judged by repetitions, not by places.

The reading "65,536 equal tasks" fails on the numbers above: a quarter of the places do almost all the work.

A few results look wrong here and are not, or the other way round. A total that differs from 16,274,722 by a little comes from different rounding, through compiler flags or a line written in another order. A total of 0, or nearly 0, means the sum read result instead of ref_result, or was taken before the reference was computed. A picture at -r 512 that shows the same shape as at 256 is correct, because img_size only sets how finely the same part of the graph paper is sampled.

Without code, the picture is made of tens of thousands of small, independent calculations, and they are wildly unequal: a quarter of them do nearly all the work, and no one can tell which before computing them. So "we split the job into equal parts" says nothing until someone checks that the parts are equal in work, not only in number.

The guess at the top has its answer: almost all, 97.7 percent of the 16,274,722 repetitions, come from the 15,902 places, 24.3 percent of the picture, that reach 1000.

A harder question to finish with. Bands of i gave 2.10 out of 4. Without knowing any count in advance, how would you split the 256 values of i between 4 workers so that each gets about a quarter of the work, and what speedup would you expect?

CHECK

Deal the values of i out in turns: worker k takes i = k, k + 4, k + 8, and so on, so each worker gets a slice of every band, cheap and costly alike. Computed on the real counts, the shares are 25.2, 25.0, 24.9 and 25.0 percent, a speedup of 3.97 out of 4, and no knowledge of the counts was needed, only that costly places sit together.

The lab pages work the same ground at length: from (i, j) to the middleman pair, the while loop by hand and the w line. The short notes on the middleman pair and on iters hold the same numbers in a minute each.
