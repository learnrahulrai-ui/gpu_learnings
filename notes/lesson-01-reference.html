Lesson 1. The reference program, by hand

This lesson covers Lab 1, part 1, on the CPU, where nothing has to be written yet: the function mandelbrot_cpu_scalar in the starter file mandelbrot_cpu.cpp is already complete. What you add to main, the function where the program begins, is a loop that adds up the numbers mandelbrot_cpu_scalar stores, and a print of the sum. You need g++ and the Lab 1 starter folder, fetched with git clone https://github.com/accelerated-computing-class/lab1.git. Paragraphs with a red rule beside them are for your pencil; work each one before opening its CHECK.

The Lab 1 starter file, mandelbrot_cpu.cpp, holds a function that is already written, mandelbrot_cpu_scalar, and an empty one, mandelbrot_cpu_vector, which part 2 of the lab asks you to write. Its main computes the written function's answer first, keeps it in an array named ref_result, and compares the vector function's answer with it, so the written function is the reference. That answer is a square sheet of whole numbers, one for each place of a picture, and each number says how many times a short loop went round at that place. A few steps of the reference look as if they do nothing. How much work does one place take, and can anyone tell before its loop has finished?

The first questions at this step were about the numbers set to 0 before the loop begins:

Write a guess before any arithmetic. Executed with nothing typed after its name, the program first prints Testing with image size 256x256 and 1000 max iterations., so the picture has 256 by 256 places, and the loop may go round at most 1000 times at one place. Of all the times the loop goes round over the whole picture, what share belongs to the places where it goes round the full 1000 times: about a quarter, about half, or almost all?

Reading mandelbrot_cpu_scalar from beginning to end

void mandelbrot_cpu_scalar(uint32_t img_size, uint32_t max_iters, uint32_t *out) {
    for (uint64_t i = 0; i < img_size; ++i) {
        for (uint64_t j = 0; j < img_size; ++j) {
            float cx = (float(j) / float(img_size)) * 2.5f - 2.0f;
            float cy = (float(i) / float(img_size)) * 2.5f - 1.25f;
            float x2 = 0.0f;
            float y2 = 0.0f;
            float w = 0.0f;
            uint32_t iters = 0;
            while (x2 + y2 <= 4.0f && iters < max_iters) {
                float x = x2 - y2 + cx;
                float y = w - x2 - y2 + cy;
                x2 = x * x;
                y2 = y * y;
                float z = x + y;
                w = z * z;
                ++iters;
            }
            out[i * img_size + j] = iters;
        }
    }
}

This is the whole function as the starter has it, with its comments left out; the first of them says that the function generates the Mandelbrot set. It takes three inputs: img_size and max_iters, two 32-bit whole numbers, and out, the address in memory where the answers go, one 32-bit whole number after another. The outer for loop gives i every value from 0 to img_size - 1, one after another, and for each i the inner for loop gives j every value from 0 to img_size - 1, so everything inside executes once for every pair (i, j), img_size times img_size times in all. For each pair, cx is j divided by img_size, times 2.5, minus 2.0, with j and img_size first turned into fractions, and cy is i treated the same way but minus 1.25; the f after each number marks a 32-bit fraction, which C++ calls a float. Then x2, y2 and w are made as floats and iters as a whole number, all 0. Before each trip through its braces, the while loop tests whether x2 + y2 is at most 4 and whether iters is below max_iters, and it makes the trip only when both hold. In the trip, x becomes x2 minus y2 plus cx; y becomes w minus x2, minus y2, plus cy; x2 becomes x times x and y2 becomes y times y; z becomes x plus y; w becomes z times z; and iters goes up by 1. Once the while loop is left, iters is stored in out at entry number i times img_size plus j.

Call one trip through the braces of the while loop a repetition; iters then counts the repetitions at one pair (i, j), and the stored number is that pair's count. Each pair is one place of the picture, and out holds img_size times img_size counts, the count of (i, j) at entry i times img_size plus j. These pages draw out as a sheet with i counting down from the top and j counting right, and call it the image paper. The pair of fractions (cx, cy) is a point on a second sheet, the plane drawn with (0, 0) at its center, which these pages call the graph paper, and (cx, cy) itself is called the middleman pair, because it stands between the place and its count: cx is computed from j alone, cy from i alone, and nothing inside the while loop reads i, j or anything that belongs to another place.

Take img_size = 256 and the place (64, 64), with i = 64 and j = 64. Work out cx = 64 / 256 * 2.5 - 2.0 and cy = 64 / 256 * 2.5 - 1.25. Then work out cx at j = 0 and at j = 255, and cy at i = 0 and at i = 255.

CHECK 
64 / 256 = 0.25,   0.25 * 2.5 = 0.625
cx = 0.625 - 2.0  = -1.375
cy = 0.625 - 1.25 = -0.625

j = 0    ->  cx = 0 * 2.5 - 2.0 = -2.0
j = 255  ->  255 / 256 = 0.99609375,  * 2.5 = 2.490234375,  - 2.0 = 0.490234375
i = 0    ->  cy = 0 * 2.5 - 1.25 = -1.25
i = 255  ->  cy = 2.490234375 - 1.25 = 1.240234375

For any img_size, j goes from 0 to img_size - 1, so j / img_size goes from 0 up to (img_size - 1) / img_size. Work out that largest value at img_size = 256 and at 512, and say whether it can reach 1 at any img_size; from that, write the values that cx and cy never reach. Then subtract the cx of j from the cx of j + 1 to get the step between neighbouring places, and work it out at 256 and at 512.

CHECK 
255 / 256 = 0.99609375 at img_size = 256,   511 / 512 = 0.998046875 at 512
(img_size - 1) / img_size = 1 - 1 / img_size, below 1 at every img_size, so
cx never reaches 1 * 2.5 - 2.0 = 0.5, and cy never reaches 1 * 2.5 - 1.25 = 1.25

((j + 1) / img_size * 2.5 - 2.0) - (j / img_size * 2.5 - 2.0) = 2.5 / img_size
2.5 / 256 = 0.009765625,   2.5 / 512 = 0.0048828125

At every img_size, cx begins at -2.0 and stays below 0.5, and cy begins at -1.25 and stays below 1.25, so the places always cover the same part of the graph paper; a larger img_size puts more places on it, closer together, at 512 half the step of 256.

Working place (64, 64) through the while loop by hand

Before repetition 1 at any place, x2 and y2 are both 0, so x2 + y2 = 0, which is at most 4, and iters is 0, below max_iters; with max_iters at least 1, every place therefore makes at least 1 repetition. After each repetition the while loop tests x2 + y2 and iters again, and it is left as soon as x2 + y2 is above 4 or iters has reached max_iters. The trip that would take iters above max_iters is never made, so every count lies between 1 and max_iters, here 1 and 1000.

Work repetitions 1 and 2 at place (64, 64), with cx = -1.375 and cy = -0.625. In repetition 1, x = 0 - 0 + cx and y = 0 - 0 - 0 + cy; from them work out x2, y2, z and w, then x2 + y2 before repetition 2. Work repetition 2 the same way from the new x2, y2 and w, and write x2 + y2 before repetition 3.

CHECK 
repetition 1:  x = 0 - 0 + (-1.375)      = -1.375
               y = 0 - 0 - 0 + (-0.625)  = -0.625
               x2 = 1.890625   y2 = 0.390625   z = -2.0   w = 4.0
before repetition 2:  x2 + y2 = 1.890625 + 0.390625 = 2.28125, at most 4

repetition 2:  x = 1.890625 - 0.390625 - 1.375         = 0.125
               y = 4.0 - 1.890625 - 0.390625 - 0.625   = 1.09375
               x2 = 0.015625   y2 = 1.1962890625   z = 1.21875   w = 1.4853515625
before repetition 3:  x2 + y2 = 0.015625 + 1.1962890625 = 1.2119140625, at most 4

Work repetition 3 from those values, write x2 + y2 before repetition 4, and say what the while loop does next, what iters is, and at which entry of out the count is stored. Then write x2 + y2 before repetitions 1 to 4 side by side.

CHECK 
repetition 3:  x = 0.015625 - 1.1962890625 - 1.375                 = -2.5556640625
               y = 1.4853515625 - 0.015625 - 1.1962890625 - 0.625  = -0.3515625
               x2 = 6.531419   y2 = 0.123596   (to 6 decimals)
before repetition 4:  x2 + y2 = 6.531419 + 0.123596 = 6.655015, above 4
the while loop is left with iters = 3, stored at out[64 * 256 + 64] = out[16448]

x2 + y2 before repetitions 1 to 4:   0,   2.28125,   1.2119140625,   6.655015

Over repetition 2, x2 + y2 went down, from 2.28125 to 1.2119140625, and one repetition later it was 6.655015, above 4, so the direction of the last change did not tell what came next; at this place only working the repetitions gave the count, 3.

Following x and y from one repetition into the next

Nothing in the loop multiplies x by y. To see what one repetition does to the pair (x, y), call the x and y that one repetition makes a and b. The rest of that repetition then leaves x2 = a times a, y2 = b times b, z = a + b and w = (a + b) times (a + b), and these are the values that the next repetition's test and its new x and y read.

Multiply (a + b) times (a + b) term by term and add the four products. Put the result into the next repetition's y, w - x2 - y2 + cy, and write its x, x2 - y2 + cx, in terms of a, b and cx. Then test both on place (64, 64): with a = 0.125 and b = 1.09375 from repetition 2, the two must give the x and y of repetition 3.

CHECK 
(a + b) * (a + b) = a * a + a * b + b * a + b * b
                  = a * a + 2 * a * b + b * b
next y = (a * a + 2 * a * b + b * b) - a * a - b * b + cy = 2 * a * b + cy
next x = a * a - b * b + cx

with a = 0.125 and b = 1.09375:
next y = 2 * 0.125 * 1.09375 + (-0.625)     = 0.2734375 - 0.625 = -0.3515625
next x = 0.015625 - 1.1962890625 + (-1.375) = -2.5556640625
as repetition 3 gave:  y = -0.3515625,  x = -2.5556640625

Each repetition turns (a, b) into (a * a - b * b + cx, 2 * a * b + cy). The new y gets 2 * a * b out of w by subtracting the two squares x2 and y2, and the test before the next repetition reads the same two squares, x2 + y2 = a * a + b * b.

Written straight from those two formulas, with x and y kept between repetitions instead of x2, y2 and w, and with x and y both 0 before the first repetition, the loop would be:

while (x * x + y * y <= 4.0f && iters < max_iters) {
    float xt = x * x - y * y + cx;
    y = 2 * x * y + cy;
    x = xt;
    ++iters;
}

Before each repetition it tests x times x plus y times y against 4 and iters against max_iters; it computes the next x into a temporary, xt, because the next y still needs the old x; it computes the next y as 2 times x times y plus cy; it moves xt into x; and it adds 1 to iters.

Count, for one repetition of each loop as written, the float multiplies and the float adds or subtracts, with the addition in the test included and its comparison with 4 left out.

CHECK

The loop written from the formulas multiplies x by x and y by y in its test and again for xt, and for the next y computes 2 times x and then times y: 6 multiplies. It adds once in its test, subtracts and adds for xt, and adds cy for the next y: 4 adds or subtracts, 10 operations in all.

The starter's loop adds once in its test, x2 + y2; subtracts and adds for x; subtracts twice and adds once for y; and adds once for z: 7 adds or subtracts. It multiplies only for x2, y2 and w: 3 multiplies, again 10 operations in all.

So both loops do 10 float operations per repetition. The starter's loop squares a and b once and reads the two squares three times, in its test, in x and in y, so it does 3 multiplies where the loop written from the formulas does 6, and 3 more adds and subtracts in their place.

Adding up the repetitions of every place

The program begins in main. Cut to what this lesson uses, main in the starter reads:

uint32_t img_size = 256;
uint32_t max_iters = 1000;
enum MandelbrotImpl impl = ALL;
if (ParseArgsAndMakeSpec(argc, argv, &img_size, &max_iters, &impl))
    return -1;
std::vector<uint32_t> result(img_size * img_size);
std::vector<uint32_t> ref_result(img_size * img_size);
mandelbrot_cpu_scalar(img_size, max_iters, ref_result.data());
if (impl == SCALAR || impl == ALL) {
    memset(result.data(), 0, sizeof(uint32_t) * img_size * img_size);
    BENCHPRESS(mandelbrot_cpu_scalar, img_size, max_iters, result.data());
    dump_image("out/mandelbrot_cpu_scalar.bmp", img_size, max_iters, result);
}
if (impl == VECTOR || impl == ALL) {
    memset(result.data(), 0, sizeof(uint32_t) * img_size * img_size);
    BENCHPRESS(mandelbrot_cpu_vector, img_size, max_iters, result.data());
    dump_image("out/mandelbrot_cpu_vector.bmp", img_size, max_iters, result);
    std::cout << "  Correctness: average output difference from reference = "
              << difference(img_size, max_iters, result, ref_result) << std::endl;
}

main sets img_size to 256, max_iters to 1000 and impl, the choice of versions to time, to all of them. ParseArgsAndMakeSpec, defined in the same file, changes img_size when the program is given -r and a size, which must be a multiple of 32, changes max_iters when given -b and a cap, and changes impl when given -i scalar or -i vector; it then prints the size and the cap it ended with, as in Testing with image size 256x256 and 1000 max iterations. main makes two arrays of img_size times img_size 32-bit whole numbers, result and ref_result, which a std::vector fills with 0, and computes the reference once into ref_result. Then, unless only the vector version was chosen, it sets result to 0 again and times the reference with the macro BENCHPRESS, which the same file defines: it calls the function 10 times, measures each call, sorts the 10 times and prints the smallest, in milliseconds. dump_image then writes the counts in result as a picture, out/mandelbrot_cpu_scalar.bmp. Unless only the reference was chosen, main does the same for mandelbrot_cpu_vector and then prints a number that the function difference, in the same file, computes from the gap between result and ref_result at every place.

To see the work of the whole picture as one number, add to main, right after the reference is computed, a for loop that adds every entry of ref_result into a 64-bit whole number, uint64_t, and a std::cout statement that prints the sum after a word such as CPU total. A 32-bit whole number holds at most 2 to the power 32 minus 1 = 4,294,967,295, and at -r 4096 the picture has 4096 * 4096 = 16,777,216 places, whose counts could add up to as much as 16,777,216 * 1000 = 16,777,216,000, so the sum needs 64 bits.

In the lab1 folder that git clone made, mkdir -p out makes the folder out, which dump_image writes into; writeBMP, the function in the same file that dump_image calls, opens the file with std::ofstream and never checks that the file opened, so without that folder the program finishes with no picture and no message. g++ -O3 -march=native -std=c++17 mandelbrot_cpu.cpp -o mandelbrot_cpu compiles the file with full optimization, -O3, allowing every instruction this CPU has, -march=native, as 2017 C++, into the program mandelbrot_cpu. ./mandelbrot_cpu executes it with the defaults, 256 by 256 places and max_iters 1000: it computes the reference, prints your sum, times the reference, and then times the still empty vector function too, printing a number about it that this lesson does not use.

Execute it and write your sum and the time printed for mandelbrot_cpu_scalar. The laptop printed a sum of 16,274,722 and a time of 61.6 ms; what would a different sum mean?

CHECK

A different sum means different counts at some places, so something in your build differs: a change in the reference, another img_size or max_iters, or a compiler that rounds some float step differently.

Computed by executing the reference's own arithmetic in 32-bit floats for all 256 * 256 = 65,536 places at max_iters 1000, the counts add up to 16,274,722, the laptop's printed sum; 3,781 places have a count of 1, and 15,902 have a count of 1000.

A place stops after 1 repetition when x2 + y2 before repetition 2 is above 4, and after repetition 1, x = cx and y = cy, so that sum is cx * cx + cy * cy. Work it out at the corner place (0, 0) and at (64, 64).

CHECK 
at (0, 0):    cx = -2.0, cy = -1.25:   4.0 + 1.5625 = 5.5625, above 4   -> count 1
at (64, 64):  1.890625 + 0.390625 = 2.28125, at most 4                -> count at least 2

A count of 1 happens exactly where cx * cx + cy * cy is above 4, and the same computation counts 3,781 such places, the 3,781 with a count of 1.

Work out the average count per place, 16,274,722 / 65,536; the share of places that reach 1000, 15,902 / 65,536; and the share of all repetitions those places make, 15,902 * 1000 / 16,274,722.

CHECK 
16,274,722 / 65,536      = 248.3 repetitions per place on average
15,902 / 65,536          = 24.3 percent of the places reach 1000
15,902,000 / 16,274,722  = 97.7 percent of the repetitions are theirs

Splitting the 256 values of i into 4 equal parts

Suppose the picture is split between 4 workers, for example 4 cores of the CPU, each of which executes its own sequence of instructions, and each worker takes a band of 64 consecutive values of i: 0 to 63, 64 to 127, 128 to 191 and 192 to 255. Computed from the same counts, the bands carry 462,567, 7,558,684, 7,747,009 and 506,462 repetitions.

Check that the four bands add up to 16,274,722. Assume every repetition takes the same time, so a worker's time follows its repetitions and the job ends when the largest band ends. Call the speedup the time of 1 worker doing all of it divided by the time of the 4 together; work it out and set it beside 4. Then work out the first and the last band as shares of the largest.

CHECK 
462,567 + 7,558,684 + 7,747,009 + 506,462 = 16,274,722
16,274,722 / 7,747,009 = 2.10, the speedup
462,567 / 7,747,009 = 6.0 percent of the largest band, for the first
506,462 / 7,747,009 = 6.5 percent of the largest band, for the last

The speedup is 2.10, not 4. The workers on the first and last bands finish after 6.0 and 6.5 percent of the time of the largest band and then wait, because the places with large counts sit together in the two middle bands.

The laptop printed 61.6 ms for the reference, which makes all 16,274,722 repetitions in one call. Work out the time of one repetition, and yours from your own time and sum.

CHECK

The time of one repetition is 0.0616 s / 16,274,722 = 3.79 ns on one core of the laptop. Dividing the whole time by the repetitions charges the rest of the function, computing cx and cy and storing the counts, to the repetitions as well.

Gathering what the numbers say about the work per place

At every img_size the places cover cx from -2.0 to below 0.5 and cy from -1.25 to below 1.25; every count lies between 1 and 1000; at (64, 64), x2 + y2 before repetitions 1 to 4 was 0, 2.28125, 1.2119140625 and 6.655015, so the direction of the last change before repetition 3 did not tell what came next; the new y gets 2 * a * b out of w, with 3 multiplies per repetition instead of 6, at the same 10 operations; 24.3 percent of the places make 97.7 percent of the 16,274,722 repetitions; 4 bands of 64 values of i give 2.10, not 4; and one repetition costs 3.79 ns on one core.

Write one sentence on what any faster version of this program has to respect about the work per place.

CHECK

A place's work ranges from 1 to 1000 repetitions, nothing on this page found a place's count without working its loop, and the places with large counts sit together, so a split of the picture between workers has to be judged by the repetitions each part carries, not by its number of places.

The reading "65,536 equal tasks" fails on two numbers above: 24.3 percent of the places make 97.7 percent of the repetitions, and equal bands gave 2.10, not 4.

A sum of 0 means your added loop read result, which main has only filled with zeros at that point, instead of ref_result. A program that finishes without out/mandelbrot_cpu_scalar.bmp was executed without the folder out. A picture at -r 512 with the same shape as at 256 is correct, since cx and cy cover the same part of the graph paper at every img_size, only with more places.

The program computes a picture of 65,536 places, and each place's number comes from a loop that reads only that place's own pair of fractions, so the places are separate calculations. They are far from equal: 24.3 percent of the places make 97.7 percent of the repetitions, the costly ones sit together, and splitting the picture into 4 equal bands gave 2.10 times the speed of one worker, not 4. "We split the job into equal parts" says nothing until someone checks that the parts are equal in work, not only in size.

The share asked for before any arithmetic is almost all: 97.7 percent of the 16,274,722 repetitions come from the 15,902 places, 24.3 percent of the picture, that reach 1000.

A split that knows no count in advance can deal the values of i out in turns: worker k, for k = 0 to 3, takes i = k, k + 4, k + 8 and so on up to 252 + k. Computed from the same counts, the four workers then carry 4,095,090, 4,066,690, 4,047,903 and 4,065,039 repetitions. Why does this split balance the work without knowing any count, and what speedup does it give?

CHECK

Each band of 64 values of i gives 64 / 4 = 16 of its values to each worker, cheap and costly alike, so every worker gets a quarter of the two costly middle bands: 25.2, 25.0, 24.9 and 25.0 percent of the 16,274,722 repetitions, and the job ends with the largest, 16,274,722 / 4,095,090 = 3.97, out of 4. Dealing in turns used no count, only that the places with large counts sit together in the two middle bands.
