The story

Lab 2 begins with a small experiment: measure how many cycles one multiply-add takes on the GPU. The starter code reads a clock counter, does 64 multiply-adds, reads the counter again, and subtracts. It looks impossible to get wrong.

It is easy to get wrong, because the compiler is free to move instructions around the clock reads. The clock read takes no input, so nothing forces the work you meant to exclude to stay outside the timed region, and nothing forces the work you meant to include to finish inside it. The learner's own compiled program is the test case.

Where exactly did the compiler put each instruction, and what does each possible placement of the clock reads include or leave out? The learner's own machine listing is the evidence.

Work it out

L01 The starter file fma_latency.cu defines the clock read, copied without change: from: code

#define clock_cycle() \
    ({ \
        unsigned long long ret; \
        asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret)); \
        ret; \
    })

L02 %clock64 is a 64-bit counter inside the GPU chip that goes up by 1 at every tick of the GPU clock. A tick of the clock is called a cycle. L01 copies the counter into ret. from: L01, PTX definition

L03 If the reads return s and e, they are e - s cycles apart. The kernel stores s in *d_start and e in *d_end, and main prints e - s. from: L02, code

L04 Your fma_latency kernel, the lines that matter, copied without change: from: your code

data_type x = *n;                  // data_type is float (using data_type = float;)

#pragma unroll
for (int i = 0; i < 64; ++i)
    x = x * 1.0000001f + 0.00000001f;

L05 *n lives in DRAM: memory chips on the graphics card, outside the GPU chip. Arithmetic reads its inputs only from registers: storage inside the chip. So x = *n becomes an instruction that copies 32 bits from DRAM into a register. In the listing of your binary it is LDG. from: L04, listing

L06 Hardware fact: the chip begins the instruction after LDG without waiting for the copy. An instruction that reads LDG's register is held until the copy arrives. The record of registers still waiting is called a scoreboard. from: Jia et al. 2019, Dissecting the NVIDIA Turing T4 GPU

L11 Fix: give the clock read inputs. A clock read whose asm lists x and y as inputs cannot begin before x and y have values. A definition of that form: from: L08

#define clock_cycle_dep2(a, b) \
    ({ \
        unsigned long long ret; \
        asm volatile("mov.u64 %0, %%clock64;" : "=l"(ret) : "f"(a), "f"(b)); \
        ret; \
    })
start_time = clock_cycle_dep2(x, y);

In plain words

A timer measures whatever the compiled program puts between its two readings, not what the source code appears to say. Compilers move instructions when nothing forbids it. The only way to know what was timed is to read the compiled instructions, and the way to control it is to make the readings depend on the values you care about.

For a manager: a benchmark number without the exact compiled code behind it is a claim, not a measurement.
