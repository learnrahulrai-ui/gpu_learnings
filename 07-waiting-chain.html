07. Lab 2: which line waits for which line

Each line uses only what the lines above it made. The grey note says which line it takes from. Fill every ____ on paper, then open CHECK.

The story

Lab 1 spread the picture over 8 numbers per instruction on the CPU and 32 threads on the GPU. Lab 2 asks a question that sounds smaller and is harder: while one of those loops is executing, how much of the time is the hardware doing nothing at all?

The answer comes from waiting. An arithmetic operation does not deliver its value at once; on the GTX 1650 it arrives about 4 cycles after the operation begins. If the next operation needs that value, it cannot begin until then. The lines inside the Mandelbrot loop are mostly like that: each needs the one before. The learner had heard the phrase "longest waiting chain" and said plainly that it meant nothing to them.

Can the chain be built from the loop's own lines, counted, and turned into a number of idle cycles? And if a second, independent set of work goes into the same loop, how much of the idle time does it fill on this particular machine?

Your words: "There is nothing which stops me from adding the original ones before I square the original ones. Everybody knows that." / "So this is something called as longest waiting chain. I don't know what it is." / "I don't even know what a group is."

In plain words

Hardware can sit idle even when a program looks busy, because each step waits for the step before it. The fix is to give the hardware independent work to do during the wait. How much that fix is worth cannot be guessed from the code alone; it depends on how long the wait is compared with how fast the hardware can begin new work, and both have to be measured on the actual machine.

For a manager: "do more things in parallel" helps only up to the point where the hardware is already full. Past that point, extra parallel work just queues.
