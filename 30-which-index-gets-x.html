The story

Lab 4 of MIT 6.S894 multiplies two large square tables of numbers, matrices, on the GPU. Every number of the result C is a sum of products of numbers of A and B, and the first kernel gives each thread of the launch one number of C. A thread learns which one from the numbers CUDA hands it: an x number and a y number for its place in its block, and the same pair for its block in the launch.

The learner had always pictured a matrix with its first index going down and its second going across, and x as across. So taking the first index of C from y felt backwards. The formula in NVIDIA's guide for numbering the threads of a block uses the block's size in x and never its size in y, which looked like a number missing from a calculation. And the statement that 32 threads execute one instruction together sounded impossible, since every thread has its own variables.

Which of the two indices of C must take the x number, and what decides it: a picture of the matrix, or something the hardware does?

In plain words

The GPU executes threads in sets of 32 with consecutive numbers, and it counts threads along one direction first. Whatever the 32 threads of one set touch at the same moment should sit side by side in memory. So the index of the result that moves through memory one number at a time has to follow the thread number that changes first, even when that feels backwards against the usual picture of a table.

For a manager: two versions of a program can give the same answer while one moves several times more data; ask which threads act together, and whether what they touch together sits together.
