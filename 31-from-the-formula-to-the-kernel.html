The story

Lab 4 of MIT 6.S894 asks for a matrix multiplication on the GPU that finishes its large test, three square matrices of 3072 by 3072 numbers, in under 45 milliseconds. The formula is short: each number of C is a sum, over k, of a number of A times a number of B. Years of school mathematics had taught the learner to read it in order: go through A, go through B, and make C.

The kernels of the course read it the other way round. They begin from C: each thread owns one number of C, and A and B appear only inside a loop over k. Then that loop is cut into pieces, and small square pieces of A and B are copied into on-chip memory as little matrices, although the learner had just accepted that matrices live in memory as flat arrays. The loop condition bk < size_k looked like a bounds check, and the size of the small arrays, BLOCK_SIZE by BLOCK_SIZE, looked arbitrary.

Where in the formula does each part of the kernel come from: the threads, the loop, the small square arrays and the comparison bk < size_k?

In plain words

Each number of the result is a sum of products, and different numbers of the result do not depend on each other, so each thread gets one result number and walks its sum itself. Threads that need the same input numbers form one block, which copies each input number once into a small fast memory on the chip and reads it many times from there. The small memory cannot hold everything the block needs, so the block walks the sum in pieces.

For a manager: a computation that reads its inputs from far memory every time can be impossible to make fast, however many processors it has; ask how many times each number fetched is used before it is fetched again.
