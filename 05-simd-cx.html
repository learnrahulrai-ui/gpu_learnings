05. SIMD cx and cy: 8 spots from 1 number

Pencil. Paper. Every blank ____ is yours. Open CHECK only after you wrote a number.

Start from zero

Page 01: square (i, j) becomes spot (cx, cy) with cx = j/256*2.5 - 2.0, cy = i/256*2.5 - 1.25. Page 04: 8 neighbouring squares of one row go into 8 lanes and share one loop, so the loop needs 8 cx values and 8 cy values in two 256-bit registers before it starts. The scalar code computed one cx per square inside its column loop. The vector code you wrote does this instead:

__m256 offsets = _mm256_set_ps(7, 6, 5, 4, 3, 2, 1, 0);
float  dx      = 2.5f / float(img_size);
for (uint64_t i = 0; i < img_size; ++i) {
    float  cy     = (float(i) / float(img_size)) * 2.5f - 1.25f;
    __m256 cy_vec = _mm256_set1_ps(cy);
    for (uint64_t j = 0; j < img_size; j += 8) {
        float  cx     = (float(j) / float(img_size)) * 2.5f - 2.0f;
        __m256 cx_vec = _mm256_fmadd_ps(offsets, _mm256_set1_ps(dx), _mm256_set1_ps(cx));
        /* page 04 loop runs here on cx_vec, cy_vec */
    }
}

Where you got stuck

"Zero to seven makes no sense, right? They are alien to me. This program never specified this floating point numbers." / "CX itself is just one number, not eight numbers. DX is just one number. Only offsets are eight numbers, right?" / "Why is the calculation of CY vector so easy?"

Step 1: why cy is one number copied 8 times

The 8 lanes are columns j to j+7 of one row i. cy depends only on i. _mm256_set1_ps(cy) writes the same float into all 8 lanes.

DO: Row i = 40 (the row from page 04). cy = 40/256 x 2.5 - 1.25 = ____ . Write the 8 lanes of cy_vec: ____ ____ ____ ____ ____ ____ ____ ____ . How many times is cy computed for the whole image? ____ .
CHECK 
40/256 = 0.15625   * 2.5 = 0.390625   - 1.25 = -0.859375
cy_vec = [-0.859375 x 8 lanes]
cy is computed once per row: 256 times.
It sits outside the j loop because nothing in it changes when j changes.

Step 3: the three inputs of fmadd

Step 2 showed: lane k's cx = lane 0's cx + k x 0.009765625. And 0.009765625 = 2.5 / 256 = dx. So you need, per lane: k times dx plus cx. _mm256_fmadd_ps(a, b, c) computes a x b + c in each lane. The 0..7 are the k of step 2; they are the "alien" numbers, and the problem forces them on you the moment 8 lanes share one j.

               lane:   0        1        2   ...    7
a = offsets        :   0        1        2   ...    7
b = set1(dx)       :   dx       dx       dx  ...    dx       dx = 0.009765625
c = set1(cx)       :   cx       cx       cx  ...    cx       cx = 0.03125 (j = 208)
                      ---      ---      ---        ---
a*b + c            :  ____     ____     ____       ____

Step 4: the argument order trap

_mm256_set_ps takes its 8 arguments from the highest lane down to lane 0. _mm256_set_ps(7, 6, 5, 4, 3, 2, 1, 0) puts 0 in lane 0. Suppose you had typed _mm256_set_ps(0, 1, 2, 3, 4, 5, 6, 7).

DO: With the wrong order, lane 0 holds offset ____ , so lane 0 (which writes column 208) gets cx = ____ , which is the spot of column ____ . Would the 8 counts be the true counts in the wrong columns, or wrong counts? ____ .
CHECK 
wrong order: lane 0 holds 7
lane 0 cx = 7*0.009765625 + 0.03125 = 0.099609375 = spot of column 215
the counts are true counts, written mirror-reversed inside every group of 8:
column 208 gets the count of 215, 209 gets 214, ... 215 gets 208.
For row 40: written 5 5 6 6 6 7 8 12 instead of 12 8 7 6 6 6 5 5.
