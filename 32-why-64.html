The story

Lab 4's second kernel, matmul_l1_reg, must finish the 3072 test in under 8 milliseconds. The learner's version begins with a handful of named numbers: each block computes a 64 by 64 tile of C and walks k in pieces of 16, and each thread computes a 4 by 4 patch of C in its own registers. Declaring a named number was easy. Where the 64 came from was not.

It is a power of two, and every tutorial uses one, so it was easy to accept out of habit. But a number kept out of habit cannot be changed safely, and the handout asks which numbers were tuned and how their values were chosen.

What decides the side of the tile a block computes, and what stops it from growing without limit?

In plain words

A block of threads copies a square piece of each input into fast memory on the chip and uses every copied number as many times as the side of the square. The chip multiplies faster than its L2 cache can deliver numbers, so each delivered number must be used at least about 45 times for the cache not to hold the work back, and 64 is the first convenient size above that. A larger square needs more fast memory per block and leaves fewer blocks to keep every part of the chip busy.

For a manager: a tuning number should come with the quantity it controls and the limits it sits between; ask for them, because a number kept only out of habit cannot be changed safely.

The interviewer's next question

Why not make each thread's patch 16 by 16 instead of 4 by 4, which cuts the reads from shared memory to 1/8 per multiply-add?

CHECK 
A 16 by 16 patch needs 256 sums in registers, plus 32 numbers for the fragments, while a
thread may hold at most 255 registers (L01). The compiler then keeps some of them in local
memory, which the Lab 4 handout says is cached in L1 and L2 but backed by DRAM, so updating
such a sum becomes a memory access. The 4 by 4 patch already brings the shared memory time
to 4.33 ms, under the 8 ms target (L09); an 8 by 8 patch, 64 sums and 1/4 read per
multiply-add, is the larger size that still fits.
