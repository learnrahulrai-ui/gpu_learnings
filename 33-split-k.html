33. Lab 5: split-k, when C has fewer tiles than the GPU has SMs

Each line uses only what the lines above it made. The grey note says which line it takes from. Fill every ____ on paper, then open CHECK. Under each piece of code, a panel reads it in English line by line. Any unfamiliar word: words used on this site.

The story

Lab 5 of MIT 6.S894 times the matrix multiplication of Lab 4 on twelve shapes instead of one. Among them is a shape that stands apart: C is only 128 by 128 numbers, but each of them is a sum of 32,768 products. With the 64 by 64 tiles of Lab 4, that C is four tiles, so the launch has four blocks of threads, on a chip with 48 identical blocks of hardware that each execute blocks of threads.

The handout's answer is called split-k: cut the sum over k into pieces, give each piece to a block of its own, and add the pieces afterwards. The learner had written partial sums for days, inside every loop of every kernel, and could not see what was new; a for loop always finishes, so what could be unfinished about its result? And the learner's version decided when to split with a test written against the number 14.

What changes when the pieces of one sum belong to different blocks, and where should the decision to split come from?

Write your guess on paper now, before any calculation on this page.

L14 Your decision of when to split: from: your code

int determine_split_k(int32_t size_i, int32_t size_j, int32_t size_k) {
    int blocks_m = (size_i + 63) / 64;
    int blocks_n = (size_j + 63) / 64;
    int total_blocks = blocks_m * blocks_n;
    if (size_k >= 16384 && total_blocks < 14) return 16;
    if (size_k >= 8192 && total_blocks < 14) return 8;
    return 1;
}

In plain words

When the result is small but each of its numbers is a very long sum, there are too few independent results to keep every part of the chip busy. Cutting each long sum into pieces gives more independent work, but the pieces must be written down separately and added in a second step, because parts of the chip working at the same time cannot wait for each other in the middle of one step. Adding the pieces in a new order can change the last digits, so the result is checked against a tolerance, not digit for digit.

For a manager: parallel hardware is only as busy as the number of independent pieces of work; when a job has fewer pieces than the hardware has units, ask whether its pieces can be cut further, and what adding them back together costs.

The interviewer's next question

Why not have every block add its piece into a C filled with 0, with atomicAdd, which makes each read-add-store of one place indivisible, instead of a workspace and a second kernel?

CHECK 
No addition is lost then, and the workspace and the second kernel go away, but C must be
filled with 0 before every launch. The 16 pieces of each number now arrive in whatever order
the blocks finish, so the last bits of C can change from launch to launch (L13), and every
place of C receives 16 indivisible additions from different SMs. The two kernels add the
pieces of every number in one fixed order, slice 0 to slice 15, so they give the same bits
every launch.
