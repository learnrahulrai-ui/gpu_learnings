11. A program counter for every thread: is the 32-thread unit useless?

Each line uses only what the lines above it made. The grey note says which line it takes from. Fill every ____ on paper, then open CHECK. Under each piece of code, a panel reads it in English line by line. Any unfamiliar word: words used on this site.

The story

Everyone learning CUDA hears that GPU threads move in lockstep, 32 at a time. The learner took that literally and found a contradiction. If 32 threads move together, there is one place in the program for all of them. But when some threads take the if side of a branch and others take the else side, they are at different places. A single place cannot be two places, and a program counter does not move backward to fetch the other side.

The learner then found the documented answer: on this GPU every thread has its own program counter. And immediately asked the sharper question: if every thread has its own program counter, what is the point of keeping 32 of them together at all?

That question can be answered with counts instead of opinions: how many instructions begin, and how much of each instruction's room for 32 threads does useful work?

Work it out

L01 A program counter is the address of the next instruction a thread will execute. After an instruction, it moves to the next address, or to a branch target. from: definition

L02 NVIDIA fact: a launch <<<B, T>>> makes B blocks of T threads each. Your GTX 1650 chip is built from 14 units NVIDIA calls SMs; each block executes on one SM. An SM handles a block's threads in units of 32 consecutive threads. NVIDIA names such a unit a warp; your lab file warp_scheduler.cu is named after it. Threads 0 to 31 of a block form warp 0. from: CUDA programming guide, SIMT architecture

L03 NVIDIA fact: a warp executes one common instruction at a time. Each instruction that begins is for the threads of the warp whose program counter is at that instruction. from: CUDA programming guide, SIMT architecture

L04 NVIDIA fact: from Volta onward, which includes your Turing GTX 1650 (sm_75), every thread keeps its own program counter. NVIDIA calls this Independent Thread Scheduling. from: CUDA programming guide, Volta Independent Thread Scheduling

L05 Take this code in warp 0, with a and b in registers: from: example

0x100:  if (threadIdx.x < 16)  a = a + 1;     // ADD
0x200:  else                   b = b * 2;     // MUL
0x300:  /* both sides continue here */

In plain words

A GPU is fast when many threads do the same instruction at the same moment. Modern NVIDIA GPUs let threads go separate ways correctly, but when they do, the card does each way one after the other, and threads not on the current way wait. A single thread taking a long, unusual path can hold 31 others idle.

For a manager: on a GPU, the expensive cases are not the common ones; they are the rare ones that make the common ones wait.

The interviewer's next question

How would you restructure such a program so that the 31 threads do not wait for the 1?

CHECK 
Separate the rare long case from the common short one: first let every thread do the short case,
and put the places that need the long case on a list; then process that list with threads that
all take the long case together. Each set of 32 then does the same instructions.
