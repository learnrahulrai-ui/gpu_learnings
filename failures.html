The failure list: how a correct-looking result goes wrong

Each entry is a mistake that produces a number that looks fine. The first fifteen come from the learner's own Lab 2 notes (F1 to F15); the rest were found while building this site. Read the left half, cover the right half, and say why it fails before reading on. Any unfamiliar word: words used on this site.

Most wrong results in performance work are not crashes. They are numbers that print cleanly, look plausible, and answer a different question than the one asked. An interviewer looking for people who measure rather than recite will put exactly these in front of a candidate. This list collects them, each with the page where the reasoning is worked out by hand.

From the Lab 2 notes

  1. F1. An assumed number reported as measured. "An FFMA takes 4 cycles" written as the GTX 1650 result before any measurement. Fails because a model value is not evidence about this chip. Worked out: page 10.
  2. F2. Timing to the last instruction begun instead of the last value ready. With 16 FFMAs in two chains, the last begins well before its value exists. Fails because the reported time leaves out the final wait. Worked out: page 09, L14.
  3. F3. FMA in the source, no FFMA in the machine listing. The compiler simplified or removed the arithmetic. Fails because the timed code is not the code you meant. Worked out: page 10, L18.
  4. F4. Comparing kernels with different FFMA counts or different timer placement. Fails because cycles per FFMA from unequal setups do not compare. Worked out: page 10, L23 and L24.
  5. F5. Assuming the listing keeps the source order. The compiler alternated loops written one after the other. Fails because conclusions about the hardware were really about the compiler. Worked out: page 10, L20.
  6. F6. The course GPU's 48 SMs used for a 14-SM laptop. Fails because every figure per scheduler is off: 192 schedulers assumed, 56 present. Worked out: page 12.
  7. F7. A slowdown blamed on "8 blocks per SM" without checking. Fails because 8 is a possible limit for this kernel, not a measured one, and the hardware limit is higher. Worked out: page 13, L10.
  8. F8. A sweep that grows in steps of 96 units of 32 threads on a GPU whose natural step is 56. Fails because each setting lands at a different point of the curve than intended. Worked out: page 12, L14.
  9. F9. An FFMA counted as 1 operation instead of 2. Fails because the reported rate comes out at half its true value. Worked out: page 13, L03.
  10. F10. Different clock speeds or temperatures compared as if equal. Fails because cycle counts and times then disagree between measurements. Record the clock with every measurement (nvidia-smi).
  11. F11. GPU time read without waiting for the GPU to finish. The launch returns at once; the work is still going. Fails because the time misses the work. The lab's timing code already waits; adding your own timing around it measures something else.
  12. F12. Setup, memory reads or clock reads inside the timed region. Fails because their cost is added to the operation being measured. Worked out: page 09.
  13. F13. Chains that read each other. Writing x into y "for convenience" makes them one chain. Fails because the measurement is of one chain, not two. Worked out: page 10, L19.
  14. F14. A single test size taken as proof of correctness for all sizes. Fails because a size like 256 can hide rounding that other sizes expose. Worked out: page 04, L22 to L24.
  15. F15. A speaker's name from a summary used in place of the slide's credited author. Fails because the source of a claim must be the source actually checked.

Found while building this site

  1. F16. Dividing one measurement by a count. For example, 281 cycles / 64 FFMAs = 4.39 "cycles per FFMA". Fails because the fixed part is spread over the count. Worked out: page 10, L05.
  2. F17. A "prediction" fitted after the measurement. "Overhead 25 to 39, so 295" when 39 = 295 - 256. Fails because a range chosen to contain the answer predicts nothing.
  3. F18. Equal numbers of items taken as equal work. For example, four bands of the picture, 16384 places each, gave 2.10 times on 4 workers. Fails because the cost per place ranges from 1 to 1000. Worked out: page 02, L25.
  4. F19. Speedup credited to the instructions instead of the data. 8-at-once code gave 7.07 times on neighbours and would give 2.23 on shuffled places. Worked out: page 05, L25.
  5. F20. More threads expected to fix a job limited by memory. Adding two arrays moves 12 bytes per add. Fails because the time is set by bytes, not by arithmetic. Worked out: T1.
  6. F21. The plain-loop sum trusted as the exact answer. Summed in order, 20 million ones give 16,777,216. Worked out: T2.
  7. F22. A course file executed unchanged on different hardware. Fails because hardware numbers written into the file describe the course machine. Worked out: page 12.
