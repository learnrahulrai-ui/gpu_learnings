T2. Summing an array: the chain, the tree, and the wrong answer

The story

Adding two arrays gives every thread its own independent piece of work. Adding up all the numbers of one array does not: every partial total depends on the totals before it. This job, called a reduction, is the second program in every GPU course, and it is where "just put it in parallel" first stops working.

The plain loop keeps one total so far and adds each number to it in turn. Each addition needs the result of the one before. The learner of this site had already met that shape in the labs and said it plainly: one of the inputs of the next step is the result of the previous step, and everybody knows it cannot start early. True. The question is what to do about it.

There is a second, quieter question that most tutorials skip. If the parallel version adds the numbers in a different order, does it give the same total? And if not, which total is right?

L01 The plain loop: from: code

for (int k = 0; k < n; ++k)
    s = s + a[k];

Read the code in English, line by line

  1. float s = 0.0f;Make a fraction named s holding 0. It will hold the total so far.
  2. for (int k = 0; k < n; ++k)Repeat the next line for k = 0, 1, 2, and so on up to n minus 1.
  3. s = s + a[k];Add the number at place k of the array to the total so far, and keep the result as the new total.

Connect the numbers

L10 DO Collect L04 (a chain of 20,000,000), L06 (19,999,999 adds in 25 levels), L07, L08, L09. The two orders do almost the same number of adds. Write one sentence on everything the tree changes, and why both changes come from the same property of the tree. from: L04, L06, L07, L08, L09

CHECK 
The tree keeps the work (19,999,999 adds against 20,000,000) but cuts the longest chain from
20,000,000 to 25, so the adds of each level can be spread over many threads; and it adds totals
of similar size, so the partial totals never get large next to what is added to them, and the
rounding of L08 never swallows a whole 1.0. Both come from pairing equals instead of adding
each new number to one ever-growing total.

Tempting answer that fails: "reordering for parallelism costs accuracy; the plain loop is the
correct one". L09 measures the plain loop 16.1 percent wrong.

In plain words

Adding up a long list can be done step after step or as a tournament of pairs. The tournament has the same amount of work but finishes in 25 rounds instead of 20 million, which is what lets a GPU help. With computer fractions it is also more accurate, because the step-after-step total grows so large that small numbers added to it are rounded away.

For a manager: two correct programs can give different totals from the same data. Ask which order of operations produced a number before trusting it to many digits.

The interviewer's next question

On real data your GPU tree sum and your CPU loop sum disagree in the fifth digit. Which do you trust, and how do you settle it?

CHECK 
Neither by default. Compute a reference with 64-bit fractions (53 significant bits instead of 24)
and compare both against it. The tree is usually closer, because its partial totals stay
similar in size, but that is a tendency, not a guarantee: the reference settles it.
