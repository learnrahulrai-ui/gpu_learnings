24. Lecture 2: an if-else when one instruction serves 8 indices

Each line uses only what the lines above it made. The grey note says which line it takes from. Fill every ____ on paper, then open CHECK. Under each piece of code, a panel reads it in English line by line. Any unfamiliar word: words used on this site.

The story

Lecture 2 of MIT 6.S894 shows 8 ALUs that all receive the same instruction, beside code with an if: if x is greater than 0, three statements; otherwise, two others. Above the ALUs it writes T T F T F F F F, one answer of the test for each, and down the page, in time, it shades the ALUs that do useful work and crosses out the others. Under it: not every ALU does useful work every cycle, and in the worst case only one in n does.

The learner had always seen an if as a jump: test, then do one side or the other. With one instruction for all 8, there is nothing to jump with, so choosing per index seemed impossible, and "useful" made no sense: every result is computed, so every result is useful. If both sides are executed, does that not break the program? And why does the compiled code compare the input instead of the result of the computation?

What, exactly, does the hardware do when 8 indices disagree about one if, and what keeps the result correct?

L04 The laptop's AVX2 has no instruction that jumps for some indices and not for others: a jump changes the address of the next instruction, and the 8 indices share one stream of instructions (L01). What AVX2 has is a compare, vcmpltps, whose result at each index is 32 bits all 1 where the test is true and all 0 where it is false, called a mask, and a bitwise AND, vandps. from: L01; Intel's intrinsics guide

With -fno-trapping-math added, which lets gcc assume that floating-point operations raise no signal the program watches (division by zero, overflow and others), the loop for 8 floats at a time becomes this, after vbroadcastss has put 10.0 into all 8 indices of ymm3 and vxorps has put 0.0 into all 8 of ymm2: from: gcc 13.3.0 output, on the machine that built this site

.L5:

Read the code in English, line by line

  1. .L5:The name of the loop's first instruction.
  2. vmulps (%rcx,%rdx), %ymm3, %ymm1Read 8 floats of x from memory (the address in rcx plus rdx), multiply each by the 10.0 in ymm3, and put the 8 products in ymm1, at every index, whatever its x.
  3. vcmpltps (%rcx,%rdx), %ymm2, %ymm0Compare the same 8 floats of x with the 0.0 in ymm2: at each index where 0.0 is less than x, put 32 one-bits into ymm0, elsewhere 32 zero-bits.
  4. vandps %ymm1, %ymm0, %ymm0AND the products with those bits, bit by bit, and put the result in ymm0.
  5. vmovups %ymm0, (%rsi,%rdx)Store the 8 results as 8 floats of y.
  6. addq $32, %rdxMove on by 32 bytes, 8 floats.
  7. cmpq %rdi, %rdxCompare with the end of the arrays.
  8. jne .L5If not at the end, jump back to .L5. This jump is the same for all 8 indices.

No: an AND can only keep a value or turn it into 0.0 (L08); -1 must come from a second
computed set of values, so the selection needs a blend (L10).

One stream of instructions cannot choose which instructions an index executes, so it
executes both sides at every index and chooses which value each index keeps, with a mask
computed from the same test: the choice moves from the next instruction's address into
the data. The price is the work of the side not taken (47.5 percent useful on the slide,
12.6 percent for one long index), and it is correct only when the discarded work cannot
be seen: no faults, no stores (L12).

Tempting answer that fails: "SIMD has no if, so it cannot do an if-else". The loop of L06
does the if-else of L05 exactly and prints 0 30 0 40 50 0 70 0.

In plain words

When one instruction drives eight arithmetic circuits, it cannot send some of them one way and the rest another. So the machine does both sides of an if for all eight, and at the end each of the eight keeps the answer its own test chose; the other answer is thrown away. The result is exactly right, but the time spent on the thrown-away side is lost.

For a manager: code that branches differently for neighbouring data executes at a fraction of the hardware's speed on vector and GPU hardware; ask how often neighbouring items take different branches.

The interviewer's next question

A GPU gives one instruction to a set of 32 threads. For the slide's if-else, what does it execute when all 32 threads have x above 0, and what changes when one thread's x is not?

CHECK 
All 32 true: every thread agrees. If the compiler kept a jump, all 32 take it and the
else side is never executed, so all of the work is useful, unlike gcc's AVX loop of L06,
which executes both sides every time; if it used predication instead, the else side's
instructions still begin, and change no thread.
One thread false: both sides execute for the set of 32, the if side changing 31 threads
and the else side 1, the others' results discarded; a GPU listing shows this either as
instructions carrying a condition (a prefix such as @P0) or as jumps with BSSY and BSYNC
around the two sides.
Data that agrees costs nothing extra; a single thread that disagrees costs the whole
other side for all 32.
