06. GPU: one changed line, and the proof of "nearby"

Each line uses only what the lines above it made. The grey note says which line it takes from. Fill every ____ on paper, then open CHECK. Under each piece of code, a panel reads it in English line by line. Any unfamiliar word: words used on this site.

The story

The graphics card in this laptop, a GTX 1650, has 896 small arithmetic units arranged in 14 SMs. Lab 1 first computes the whole picture with one GPU thread, which takes 403 milliseconds, more than six times slower than one CPU core. Then it changes one line so that 32 threads share the work, and the time falls to 17.7 milliseconds.

The changed line makes thread number t take the places j = t, t + 32, t + 64, and so on. The chat claimed this made memory access efficient because neighbouring threads touch nearby memory. The learner refused the claim without proof: inside thread 7 the places 7 and 39 are far apart, threads do not talk to each other, so where is the nearby?

The only evidence that settles it is a pair of profiler counts the learner's own machine printed: 2,048 and 8,192. And once that is settled, a second question nobody in the chat asked: did the same one-line choice decide anything besides memory?

Your words: "no proof this how can 7 and 39 and all be nearby stuff" / "On one hand you are saying nearby, and on one hand you are saying spacing. You cannot space out and do nearby at the same time" / "Threads don't talk to each other. A thread doesn't know about other threads, right?"

In plain words

On a GPU, the decision of which thread handles which piece of data is the most important line in the program. Here a single line decided both how much memory traffic there is and how much of the arithmetic is wasted waiting. Getting it wrong does not produce an error; it produces a correct picture, slower.

For a manager: a GPU program can be correct and still leave most of the card idle. Only measurements like the profiler counts on this page reveal which.
