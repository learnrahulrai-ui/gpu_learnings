The story

NVIDIA Warp, the Python library for GPU kernels, decides by itself how much of an SM's shared memory each kernel needs, and asks for exactly that much when the kernel is launched. In November 2026 Warp issue 2294 reported a kernel that crashes with an illegal memory access although it never touches memory by hand: it calls a small helper that returns a tile, and then uses that tile in a matrix product.

The reporter found it in MuJoCo Warp, a physics engine built on the library. The learner, reading it as an application developer, could not see how correct operations, each valid on its own, could add up to an illegal access, and why other sizes of the same kernel did not crash.

How can a kernel that addresses nothing by hand ask for too little memory, and why would the same mistake crash at one size and not at another?

L01 NVIDIA Warp issue 2294, opened on 11 November 2026 and still open: with K = 16, N = 20 and blocks of 128 threads, the kernel below is launched once (decorators and argument types left out). A tile is a piece of an array that the threads of a block hold together, kept either in their registers or in the block's shared memory. Warp computes the shared memory the kernel needs and requests it at the launch. from: NVIDIA Warp issue 2294

def double_tile(a):

    return wp.tile_map(wp.add, t, t)
J_kj = wp.tile_load(J, shape=(K, N), storage="shared")
d = double_tile(a)
J_ki = wp.tile_map(wp.mul, wp.tile_transpose(J_kj), wp.tile_broadcast(d, shape=(N, K)))

L04 The issue's explanation: "The tile returned by a user function shares its type object with the variable that receives it in the caller", and the call is counted when it is compiled, "while the function's tile is still a register tile". CHECK 
The library counted the shared memory of the helper's call at a moment when the returned tile
still lived in registers, and a later line of the caller moved that same tile into shared
memory without the count being updated, so the kernel asked for exactly that tile's 64 bytes
too little; whether the shortfall crashes depends on the sizes, so a launch that succeeds says
nothing about the request.

Tempting answer that fails: "an illegal memory access means my code read outside an array".
The kernel addresses no memory by hand; the library's own request was 64 bytes short (L03).

In plain words

The library added up how much fast memory a program would need before the program had finished deciding where one of its pieces would live. A later step moved that piece into the fast memory, but the total was never updated, so the program asked for slightly too little. Sometimes the shortfall caused a crash and sometimes it did not, which is why ordinary testing did not catch it.

For a manager: a total computed before every decision is made can be wrong without any single step being wrong; ask when a budget is computed relative to the choices it depends on.
